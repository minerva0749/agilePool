## 2. 总体架构

```text
Submit / SubmitCtx / SubmitBefore
        │  Submit:          ctx = Background, 无 deadline
        │  SubmitCtx:       允许 ctx 在等待空间时取消；nil ctx 视为 Background
        │  SubmitBefore:    deadline = now + timeout，"开始执行"期限
        ▼
taskQueue（queue.mu 保护）
  chunk FIFO：head ──► … ──► tail
  每个 chunk 预分配 tasks[MaxChunkLen]；count/read 记录块内状态
  notEmpty / notFull / closedCh 只做唤醒提示
        │ pop()（唯一消费者）
        ▼
dispatcher goroutine
  · 队列空且未关闭 → 阻塞在 queue.pop
  · pop 到任务后先 abortErr()，已取消/超期则 finishTask(skipped) 丢弃
  · idle 非空 → 取一个 worker，send 一个任务
  · running < Capacity → makeWorker(firstTask) 新建 worker
  · 否则等待 workerFree（idle 出现或容量槽释放）
        ▼
worker goroutine
  tasks chan（cap=1）
  循环：runTask(t) → finishTask(outcome) → pushBack(wk)
        → 等下一个任务 / idle timeout / drained
```

职责划分：

| 部件 | 职责 | 不负责 |
|---|---|---|
| submitter | 构造 `task`、检查入参、在队列满时阻塞或快速失败 | 不决定任务是否执行 |
| `taskQueue` | 保存已接受任务，维护 FIFO、长度上限、关闭状态；接受任务时回调 `onAccept` | 不执行任务、不维护 pending 计数 |
| dispatcher | 唯一消费者；从 idle 认领 worker 或按需新建；丢弃取消/超期任务并 `finishTask` | 不执行任务、不回收 idle（worker 自己回收） |
| worker | 执行 `runTask`、recover panic、`finishTask` 后回到 idle | 不改变队列状态、不直接操作 pending |

`Pool.pending` 是唯一的 pending 计数者；`taskQueue` 只在“任务已写入 chunk”的同一临界区
回调 `onAccept`，让“接受”与“pending +1”原子化（第 6.1 节）。

与上游 `reference-agilePool` 的关系：

- 参考点：任务缓冲、idle worker 复用、按需扩容、idle timeout 缩容、后续 hook/metrics 能力。
- 主动保留的不同：`TaskFunc` 显式携带 `ctx`；`Submit` 返回错误而不是静默丢弃；
  dispatcher 单消费者 + `idle []*worker`，而不是 worker 自己从共享队列拉取；
  `WaitGroup` 按 worker 计数而非按任务计数；`WaitPool` 要求先 `Close`。
- 这些差异是 v4/v5 已确定的设计，不因为"上游不是这样"而改。

## 3. 任务状态机与所有权（当前行为）

### 3.1 状态转移

| 状态 | 进入条件 | 持有者 | 离开路径 |
|---|---|---|---|
| S0 提交中 | 调用 `Submit*` | submitter | 拒绝（见 3.2）或入队 → S1 |
| S1 排队中 | `queue.pushLocked` 成功 | `queue.mu` 保护的 chunk | dispatcher `pop` → S2；Close 后仍会被 pop |
| S2 dispatcher 持有 | `queue.pop` 返回 | dispatcher 的局部变量 `t` | `abortErr` 非空 → `finishTask` 终态；否则等 worker → S3 |
| S3 已认领、待交接 | 从 idle 取走 worker 或 `makeWorker(firstTask)` | worker 的 `tasks` channel（cap=1） | worker 收到 → S4 |
| S4 执行中 | `runTask` 开始 | worker goroutine 栈 | `runTask` 返回 outcome → `finishTask` → 终态 |
| S5 终态 | 见 3.3 | 无 | — |

### 3.2 拒绝路径（任务从未入队）

- `SubmitCtx` 的 ctx 在入队前已取消 → 返回 `context.Canceled`。
- `SubmitBefore` 的 deadline 在入队前已过（含 `timeout <= 0`）→ 返回 `context.DeadlineExceeded`。
- 队列已关闭 → 返回 `ErrPoolClosed`。
- `Mode == NONBLOCK` 且队列已满 → 返回 `ErrPoolFull`。
- `fn == nil` → 返回 `ErrNilTask`（T2 起）：任务不会入队，也不会启动 worker；
  该检查先于 ctx、池关闭和 timeout 判断。

拒绝路径不占 pending（T3 之后同样不应增加 pending）。

### 3.3 终态（当前实现）

| 终态 | 触发点 | T3 内部表示 | 当前可观测性 |
|---|---|---|---|
| completed | `Fn` 返回 `nil` | `resultCompleted` | 无公开计数、无 hook |
| returned error | `Fn` 返回非 nil | `resultError`，error 保存在 `taskOutcome.err` | 仍不回调、不计数；T6 引入 `ErrorHandler` |
| panic | `Fn` panic | `resultPanic`，recover 值保存在 `panicVal` | `log.Printf("task panic: %v")`，无 stack trace |
| canceled skipped | S2 的 `abortErr` 或 S4 入口检查 | `resultCanceled` | 内部 `finishTask` 记账，无公开记录 |
| deadline skipped | 同上 | `resultDeadlineSkipped` | 同上 |

### 3.4 所有权与 pending 记账（T3 起）

| 阶段 | 谁拥有 task | 谁负责 pending |
|---|---|---|
| S0 提交中 | submitter 栈 | 不增加；`push` 被拒绝时也不记账 |
| S1 排队中 | `taskQueue`（`queue.mu`） | 接受时在 `queue.mu` 内回调 `onAccept` → `pending.add()` |
| S2 dispatcher 持有 | dispatcher 栈 | 丢弃时 `finishTask(outcomeForAbort(...))` → `pending.done()` |
| S3/S4 worker 持有 | worker / `runTask` 栈 | `finishTask(runTask(t))` → `pending.done()` |
| S5 终态 | 无 | — |

“恰好一次”依赖所有权转移，而不是额外的去重结构：

- `push` 成功 → 所有权归队列；dispatcher 是唯一 `pop` 者，pop 后要么 `finishTask`，
  要么交给 worker；
- 交给 worker 后，`runTask` 必定返回一个 `taskOutcome`，worker 随即 `finishTask`；
- dispatcher 的丢弃分支与交接分支互斥，不存在“既丢弃又发送”；
- worker 的 `drained` 分支收到的最后一个任务同样走 `finishTask(runTask(t))`；
- dispatcher 只在“队列已关闭且为空”时退出，因此不会留下无人认领的已接受任务。

重复扣减会把计数减成负数，测试以 `pending != 0` 兜底（见 `TestPending*`）。

S0 的“正在提交”不计入 pending，但由 `submitting` 记录，供 `WaitIdle` 等待（T4）：
`enqueue` 在 `push` 前 `beginSubmit`、返回后 `endSubmit`。因此 `WaitIdle` 不会在
提交者仍阻塞于满队列时提前返回，而 `Pending()` 指标的语义保持不变。

### 3.5 已确认语义（T0，2026-11-22 确认）

1. `pending` 只统计**已接受**（已入队/已派发）任务，S0 中尚未入队的提交不计入。
2. 终态固定为 `completed / returned error / panic / canceled skipped / deadline skipped`；
   `Completed` hook 不覆盖 skipped 任务，skipped 单列。
3. 普通任务返回的 error 只做回调 + 计数，**不自动重试**；重试只属于 T10 的 `TaskWithRetry`。
4. `Running` 保持"存活 worker（含 idle）"语义；`Busy` 另设，不改变 `Running`。
5. `Close` 后 `WaitIdle` 仍可等待已接受任务归零；`WaitPool` 仍要求先 `Close`。
6. `fn == nil` → `ErrNilTask`（T2 已实现），与"提交失败不增加 pending、不影响后续任务"一致。

## 4. 公开 API

以下是当前代码的**准确签名**（`pool_interface.go`）：

```go
func New(cfg Config) (*Pool, error)

func (p *Pool) Submit(fn TaskFunc) error
func (p *Pool) SubmitCtx(ctx context.Context, fn TaskFunc) error
func (p *Pool) SubmitBefore(fn TaskFunc, timeout time.Duration) error

func (p *Pool) Close()
func (p *Pool) WaitPool()
func (p *Pool) WaitIdle()
func (p *Pool) Running() int

type TaskFunc func(ctx context.Context) error

type BlockMode int
const (
	BLOCK BlockMode = iota
	NONBLOCK
)

var (
	ErrPoolClosed     = errors.New("pool: closed")
	ErrPoolFull       = errors.New("pool: task buffer full")
	ErrNilTask        = errors.New("pool: nil task")
	ErrTaskBufferFull = ErrPoolFull // 历史别名
)
```

### 4.1 提交接口的区别

| 接口 | 任务 ctx | deadline | 队列满（BLOCK） | 队列满（NONBLOCK） |
|---|---|---|---|---|
| `Submit` | `context.Background()` | 无 | 阻塞直到有空位/关闭 | `ErrPoolFull` |
| `SubmitCtx` | 调用者提供（nil 视为 Background） | 无 | 阻塞，但可被 ctx 取消 | `ErrPoolFull` |
| `SubmitBefore` | `context.Background()` | `now + timeout` | 阻塞，可被 deadline 打断 | `ErrPoolFull` |

三者的共同语义：

- 返回 `nil` **只表示"已接受并入队"**，不表示已经执行，也不表示一定执行
  （之后仍可能因 ctx 取消或 deadline 过期被跳过）。
- 返回错误时任务没有入队，也没有启动任何执行。
- `fn == nil` 在三个接口上都返回 `ErrNilTask`，不会入队，也不会依赖 worker recover 才发现。

### 4.2 `SubmitBefore` 的两层语义

`timeout` 是"**开始执行**的最后期限"，不是"执行时长上限"：

1. 在等待队列空位时超时 → 返回 `context.DeadlineExceeded`，任务不入队。
2. 已入队但出队/开始执行时已过期 → 任务被跳过，不执行 `Fn`。
3. 已经交给 `Fn` 之后，池子不会因为 deadline 到期而中断它；`Fn` 拿到的 ctx 是
   `context.Background()`，需要时由调用者自己用 `SubmitCtx` 控制。

`timeout <= 0` 属于调用方参数错误：立即返回 `context.DeadlineExceeded`，不进入队列等待，
也不看池状态（这是第 4.5 节优先级里的唯一例外，测试
`TestNonPositiveTimeoutIsArgumentError` 固定了这一点）。

### 4.3 关闭与等待

- `Close()`：幂等、不阻塞；停止接收新任务，已接受任务继续由 dispatcher 排空。
  并发 `Close` 由 `sync.Once` + `queue.closed` 双重保护。
- `WaitPool()`：等待 dispatcher 和所有 worker 退出；**必须在 `Close()` 之后调用**，
  否则 dispatcher 会一直等队列，`WaitPool` 不会返回。Wait 返回后重复调用会立即返回。
- `WaitIdle()`：等待“已接受 + 正在提交”的任务全部到达终态，但不关闭池。
  空池立即返回；不需要先 `Close`；多个 goroutine 可以同时等待；一批完成后可以再次
  等待下一批。等待范围包含阻塞在满队列上的 `Submit`（`submitting` 计数），但 `pending`
  指标本身仍只统计已接受任务（T0 第 1 条）。它是“批次快照”语义：等待期间新提交的
  任务属于下一批，不保证被本次 `WaitIdle` 覆盖。`Close` 之后仍可调用，用于等待已接受
  任务排空；池退出等待仍用 `Close + WaitPool`。不要从任务函数内部调用 `WaitIdle`
  （任务自己也是 pending，会等自己造成永久阻塞）。
- `Running()`：当前存活 worker 数，包含 idle worker，不包含 dispatcher。

### 4.4 最小示例

```go
p, err := pool.New(pool.Config{
	Capacity:    4,
	IdleTimeout: time.Second,
	MaxChunkLen: 64,
	MaxBuffered: 1024,
	Mode:        pool.BLOCK,
})
if err != nil {
	return err
}

if err := p.Submit(func(ctx context.Context) error {
	// 任务逻辑；返回 error 目前不会被池子消费（T6 引入 ErrorHandler）
	return nil
}); err != nil {
	// nil 只表示已入队；这里拿到的是拒绝原因
	return err
}

p.Close()    // 停止接收，dispatcher 开始排空
p.WaitPool() // 等 dispatcher 与所有 worker 退出
```

### 4.5 提交错误优先级（T2 固定）

| 优先级 | 条件 | 返回 |
|---|---|---|
| 1 | `fn == nil` | `ErrNilTask` |
| 2 | `SubmitBefore` 且 `timeout <= 0` | `context.DeadlineExceeded` |
| 3 | 队列已关闭（`Close` 之后） | `ErrPoolClosed` |
| 4 | 任务 ctx 已取消/已到期 | `ctx.Err()` |
| 5 | 任务 deadline 已过（等待空间期间） | `context.DeadlineExceeded` |
| 6 | `NONBLOCK` 且队列满 | `ErrPoolFull` |

为什么这样排：

- 1–2 是参数错误，不依赖池状态，先于任何状态判断；
- 3 是池的终态：`Close` 之后所有提交稳定返回 `ErrPoolClosed`，producer 循环不需要
  再区分"是关闭还是恰好 ctx 取消"；
- 4–5 是任务级运行时条件，按"先 ctx 后 deadline"排序；
- 6 只在队列确实满且调用方选择 `NONBLOCK` 时出现。

实现位置：1–2 在 `Submit / SubmitCtx / SubmitBefore` 入口完成；3→4→5→6 在
`taskQueue.push` 的 `queue.mu` 内判定。`push` 从 `select` 醒来后不直接返回，
而是回到循环顶部重新判定，保证关闭与取消同时发生时仍按上表返回。

## 5. Config 配置说明

| 字段 | 默认值 / 零值行为 | 合法范围 | 说明 |
|---|---|---|---|
| `Capacity` | 无默认；`<= 0` 时 `New` 返回 error | `> 0` | worker 数量上限，也是并发执行上限 |
| `IdleTimeout` | `<= 0` → `1s` | 任意时长 | worker 空闲多久后退出；退出后容量槽释放 |
| `MaxChunkLen` | `<= 0` → `64` | `> 0` 才有效 | 每个 chunk 预分配的任务槽数 |
| `MaxBuffered` | `0` → `MaxChunkLen`；`-1` 不设限 | `-1` 或 `>= 1`；`< -1` 返回 error | **只限制队列中任务数**，不含执行中任务与 dispatcher 持有的任务 |
| `Mode` | 无默认 | `BLOCK` / `NONBLOCK` | 队列满时阻塞提交还是返回 `ErrPoolFull` |

关系：

- `MaxBuffered` 不必是 `MaxChunkLen` 的倍数；队列按 chunk 链增长，
  实际占用约 `ceil(MaxBuffered/MaxChunkLen)` 个 chunk。
- `Capacity` 与 `MaxBuffered` 相互独立：前者限制"同时执行"，后者限制"排队"。
- `MaxBuffered = 0` 被解释为"一个 chunk"，不是"零缓冲"；当前实现没有"零缓冲"配置，
  最小缓冲就是一个 chunk。需要"队列满时快速失败"请用 `NONBLOCK`，而不是把
  `MaxBuffered` 设成 0。
- 配置的默认值与校验集中在 `normalizeConfig`（由 `New` 调用）；非法组合返回 error，
  不会启动 goroutine。

## 6. 核心并发不变量

### 6.1 锁、channel 与计数

| 对象 | 保护/含义 | 只在哪里修改 |
|---|---|---|
| `p.mu` | 保护 `p.idle`、`p.running` | 所有 idle 增删、running 加减 |
| `queue.mu` | 保护 `head/tail/taskNum/closed` 及 chunk 的 `tasks/next/read/count` | `pushLocked`、`popLocked`、`close`、`size` |
| `q.notEmpty`（cap=1） | "队列可能非空"的提示 | `signalNotEmpty` |
| `q.notFull`（cap=1） | "队列可能有空位"的提示 | `push` / `pop` 之后 |
| `q.closedCh` | 队列关闭广播 | `queue.close` 中 `close` 一次 |
| `p.workerFree`（cap=1） | "可能有 idle worker 或容量槽释放"的提示 | `pushBack`、`decRunning` |
| `p.drained` | dispatcher 排空并退出后关闭 | dispatcher 的 defer |
| `p.wg` | dispatcher 1 + 每个 worker 1；**不按任务计数** | `New`、`makeWorker`、goroutine 退出 |
| `p.onceClose` | `Close` 幂等 | `Close` |
| `p.pending.mu` | 保护 `pending`/`submitting` 两个计数与可重建的 drain channel；等待条件是两者之和为 0 | `add`（仅在 `queue.mu` 内回调）、`done`（`finishTask`）、`beginSubmit`/`endSubmit`（`enqueue`）、`wait`/`snapshot` |

所有提示 channel 都允许"提示过期"：等待者醒来后必须在锁内重新检查真实条件，
不能假设"收到信号就一定有空间/worker"。

锁顺序固定为 `queue.mu → pending.mu`：`pushLocked` 在持有 `queue.mu` 时回调 `onAccept`
→ `pending.add`；`finishTask` 只获取 `pending.mu`，不获取 `queue.mu`，因此不存在反向
锁环。`beginSubmit`/`endSubmit` 在 `queue.mu` 之外获取 `pending.mu`，同样不反向持有
`queue.mu`。用户任务、日志、后续 hook 都不在这两个锁内执行。

### 6.2 worker 交接保证

1. dispatcher 从 `p.idle` 取走一个 worker 后，**必须向它的 `tasks` send 恰好一个任务**；
   中途取消也不能改发"跳过信令"或直接放弃，否则 `Close` 路径里阻塞的
   `t = <-wk.tasks` 会永久等不到任务。
2. `makeWorker(firstTask)` 用 `firstTask` 启动，**不能再 send 一次**，否则重复执行。
3. worker 的 idle timeout 与 dispatcher 认领同时发生时，`removeIdle` 返回 `false`
   说明它已被认领；worker 必须回到 `select` 继续等任务，不能直接退出。
4. worker 收到 `drained` 时先 `removeIdle`：返回 `true` 才能退出；返回 `false`
   说明已被认领，此时 dispatcher 一定会在 `close(p.drained)` 之前完成 send，
   所以可以安全地 `t = <-wk.tasks` 收下最后一个任务并执行。
5. 任务在 S3/S4 期间被取消时，当前由 `runTask` 的 `abortErr` 跳过执行，
   但 worker 仍会被占用一次"检查"；这是语义上可接受的，T5 只优化 S2 的等待。
6. 被接受的任务必须且只能经过一次 `finishTask`：S2 丢弃、S3/S4 执行、worker 的
   `drained` 分支各调用一次；不存在"队列里还有任务但 dispatcher 已退出"的路径。

### 6.3 Close / Wait 的顺序

- `Close` 先 `queue.close`（锁内置 `closed=true`，再关 `closedCh`），此后 `push` 必然
  失败，不存在"dispatcher 已退出但队列还能成功入队"的窗口。
- `push` 的错误优先级在锁内判定：`closed` > `ctx.Err()` > deadline > `ErrPoolFull`。
  因此 `Close` 后即使任务的 ctx 同时取消，提交方仍稳定收到 `ErrPoolClosed`（见 4.5）。
- dispatcher 只在"队列已关闭且为空"时退出，然后 `close(p.drained)`；
  因此 `drained` 关闭时所有已接受任务都已完成派发。
- `WaitPool` 依赖 `p.wg`：dispatcher 退出 + 所有 worker 退出。它不感知单个任务的完成，
  所以 `WaitPool` 不能替代任务级等待；任务级等待是 T4 的 `WaitIdle`。
- `Close → WaitPool` 返回时 pending 必须为 0：dispatcher 退出前已把所有任务交给
  worker，worker 退出前已执行并 `finishTask`；`TestPendingZeroAfterCloseAndWait`
  固定这一点。
- 关闭路径推荐顺序：`Close → WaitIdle → WaitPool`。`WaitIdle` 只等任务终态，不等待
  dispatcher/worker 退出；`WaitPool` 等待 goroutine 收尾。两者职责不同，
  `TestCloseWaitIdleWaitPool` 固定该组合。

### 6.4 当前已知的薄弱点（留给 T8/T9）

- `p.idle` 注释写"slice 当栈用"，实现却从头部 `p.idle = p.idle[1:]` 弹出，语义是 FIFO；
  `removeIdle` 的 `append(p.idle[:i], p.idle[i+1:]...)` 会在尾部留下陈旧 `*worker` 引用，
  底层数组容量也不会回收。T8 统一语义并清理引用。
- `queue.pop` 每次成功都无条件 `signalNotFull`；`push` 在仍有空位时继续转发 `notFull`。
  这些是无条件 channel 操作，属于 T9 的优化范围。
- `SubmitBefore` 只要带 deadline 就创建 `time.Timer`，即使队列立即有空位；
  属于 T9 的 timer 分配优化点。

## 7. 错误、panic、hook 与指标

### 7.1 当前实现

- 任务返回的 error：`runTask` 返回 `taskOutcome{result: resultError, err: err}`；
  `finishTask` 先记账，再调用 `observeOutcome`，后者目前不处理 error。error 只保存在
  内部 outcome 里，T6 才会交给 `ErrorHandler`。
- panic：`runTask` 的 `defer recover()` 捕获为 `resultPanic`；`finishTask` 先扣账，
  再由 `observeOutcome` 输出 `log.Printf("task panic: %v", ...)`。`observeOutcome`
  自身有 recover 隔离，日志出错不会打断 worker；没有 stack trace，也没有 `PanicHandler`。
- 没有 `Logger`、`ErrorHandler`、`PanicHandler` 配置项；日志走标准库全局 logger。
- 没有生命周期 hook（`Submitted/Enqueued/Started/Completed/PoolClosed`）。
- 没有公开指标；内部 `pendingTracker` 记录 `pending`（已接受、未终态）与
  `submitting`（正在 Submit）两个计数，`WaitIdle` 已接入 `wait`，但两个计数都只有
  包内 `snapshot`/`submittingSnapshot`，没有公开的 `Pending()`。公开的只有
  `Running()`；queue 长度是包内 `size()`（测试/基准使用）。
  没有 `Pending/Queued/Idle/Busy/Capacity/WorkerCreateCount`。
- 用户任务在 worker goroutine 中执行，不持有 `p.mu` 或 `queue.mu`；但这只是因为当前
  没有 hook/回调，T6 引入时仍需显式保证"回调不在锁内执行"。
- `queue.push` 里的 `ctx.Err()` 在锁外读取：自定义 `context.Context` 的 `Err` 方法属于
  用户代码，不应在 `queue.mu` 持有期间调用；代价是"读取后、加锁前"被取消的任务仍可能
  入队，随后由 dispatcher/worker 的 `abortErr` 跳过。

### 7.2 计划（T6/T7）

- T6：Logger / ErrorHandler / PanicHandler / stack trace / 生命周期 hook；
  handler 与 hook 的 panic 必须隔离，且不能绕过 pending 记账。
- T7：`Pending/Queued/Running/Idle/Busy/Capacity/WorkerCreateCount`；
  指标允许瞬时快照，但定义必须与代码一致，且不能为 metrics 在热路径新增全局锁。

## 8. 重试设计（T10，尚未实现）

尚未实现，先固定以下约束，避免 T10 走偏：

- `RetryNum` 表示**额外重试次数**，总执行次数为 `RetryNum + 1`。
- 一个逻辑任务只增加一次 pending，所有尝试结束后只减少一次。

### 9.4 端到端基准（GOMAXPROCS=12，`-benchtime=200ms`，3 次中位数）

配置均为 `Capacity=32`、`MaxChunkLen=64`、`IdleTimeout=1s`、`Mode=BLOCK`；
计时范围都包含提交、任务执行和 `Close+WaitPool` 排空；计时前预热 32 个任务。

| Benchmark | 负载 | MaxBuffered | ns/op | B/op | allocs/op | peak-queue | peak-workers |
|---|---|---|---|---|---|---|---|
| `BenchmarkEndToEndNoop` | 空任务 | 4096 | 744.4 | 66 | 0 | 4096 | 32 |
| `BenchmarkEndToEndShort` | 32 次乘加 | 4096 | 759.0 | 66 | 0 | 4096 | 32 |
| `BenchmarkEndToEndLong` | `Sleep(200µs)` | -1 | 18972 | 62 | 0 | 12849 | 32 |
| `BenchmarkEndToEndBurst` | 突发 + `Sleep(100µs)` | 256 | 18560 | 62 | 0 | 256 | 32 |
| `BenchmarkSustainedEndToEnd` | 12 producer 持续提交空任务 | 4096 | 1134 | 66 | 0 | 4096 | 32 |

说明：

- `peak-queue`/`peak-workers` 是 1ms 一次的采样峰值，不是精确计数。
- 空任务/短任务/持续提交在 4096 有界队列下进入**背压稳态**：单 producer 的提交速度
  高于 32 个 worker 的消费速度，因此 `peak-queue` 恒等于 `max-buffered`。
  这本身是有意义的观测，但不代表"队列平均值是 4096"。
- `Long`/`Burst` 的 ~19µs/任务 ≈ `Sleep(200µs)` 实测约 0.6ms ÷ 32 个并发 worker。
- `Sustained` 三次结果为 877 / 1134 / 1526 ns/op，方差明显大于批次基准；
  对比时建议同机、同命令、至少 3 次取中位数。

| Benchmark | GOMAXPROCS=1 | =4 | =12 |

| `EndToEndNoop` | 837.1 ns/op | 711.2 | 938.1 |

### 9.6 基准实现过程中的两个坑（记录，避免后续重复踩）

1. **不要用 CPU 忙等模拟长任务**：本机 `busyWait(200µs)` 实测约 2.1ms，
   在低 `GOMAXPROCS` 下被放大得更厉害（探针：1 核 2.24ms、4 核 2.15ms、12 核 1.73ms）。
   长任务改用 `time.Sleep(200µs)`（实测约 0.6ms），更接近阻塞型任务，也不会占满 P。
2. **端到端基准必须预热**：不预热时 producer 在启动阶段会把 4096 缓冲一次灌满，
   `peak-queue` 恒等于 `MaxBuffered`，且 ns/op 混入启动瞬态；预热 Capacity 个任务后，
   峰值和 ns/op 才反映稳态负载。

### 9.9 T4 WaitIdle 记账的开销（A/B，不构成正式性能结论）

用 `my_practice/v5/source/.gotmp/t3check` 下的临时副本移除 `enqueue` 中的
`beginSubmit/endSubmit`（模拟 T3 代码），与 T4 在同一台机器上顺序运行：
`BenchmarkSubmitParallel` 用 `-benchtime=50ms -count=3`；

| Benchmark | T3 等价（无 submitting） | T4（含 submitting） |
|---|---|---|
| `SubmitParallel-2` | 96.7 / 111.0 / 130.0 ns/op | 160.8 / 210.9 / 211.5 ns/op |

## 10. 兼容性、限制与后续计划

### 10.1 兼容性

- **nil task 行为变更（breaking）**：T2 前 `Submit(nil)` 会被接受并返回 `nil`，
  worker 内 panic 后被 recover；T2 起三个提交接口都返回 `ErrNilTask`。
  迁移：调用方应先检查 `fn != nil`；若要保留"跳过 nil"的行为，自行在提交前过滤。
- **错误优先级变更**：`Close` 之后即使任务 ctx 已取消/已过期，提交也返回
  `ErrPoolClosed`（T2 前可能返回 `context.Canceled` / `DeadlineExceeded`）。
  迁移：用 `errors.Is(err, ErrPoolClosed)` 判断停止提交。
- `Config` 字段与默认值行为不变，只是默认值/校验集中到 `normalizeConfig`。
- 现有示例 `main.go` 不受影响。
- T3 没有公开 API 或提交/关闭语义变化；变化都在包内：任务结果从"被丢弃"变为
  `taskOutcome` 记录，`pending` 计数只在包内可见。唯一的可观测差异是 panic 日志
  现在在扣账之后输出（内容不变）。
- `TestTerminalPathsPoolStaysConsistent` 仍用"执行次数 + queue.size + Running"作为
  一致性代理；pending 归零由 T3 的 `TestPendingZeroAfterCloseAndWait` 单独覆盖。
- **`WaitIdle` 行为变更（T4）**：T4 之前是空实现、调用立即返回；现在会阻塞等待

### 阶段 1：T2–T5

#### T2（已完成）

- 设计决策：
  - nil task 是调用方参数错误，统一在三个公开入口返回 `ErrNilTask`，不进入队列，
    也不依赖 worker recover；这比"在 queue 内拒绝"更早、更便宜。
  - 错误优先级固定为：参数错误（nil / 非正 timeout）> 池关闭 > ctx > deadline > 队列满。
    "关闭优先于 ctx/deadline"让 Close 之后的提交只有一个稳定答案，producer 循环不需要
    处理多种竞争错误；代价是调用方在池关闭后看不到 ctx 错误。
  - 优先级判定集中到 `queue.push` 的锁内循环：`select` 醒来后回到顶部重判，
    避免 Go `select` 随机选择导致同一竞争场景返回不同错误。
  - 配置默认值与校验集中到 `normalizeConfig`，`New` 只负责构造；零值行为保持不变
    （`MaxChunkLen` 64、`MaxBuffered` 一个 chunk、`IdleTimeout` 1s、`Capacity`/`Mode` 必填）。
- API/内部结构变化：
  - 新增 `ErrNilTask`；
  - 新增常量 `defaultMaxChunkLen`、`defaultIdleTimeout` 和 `normalizeConfig`；
  - `Submit/SubmitCtx/SubmitBefore` 增加 nil 检查；`SubmitBefore` 的 nil 检查先于 timeout；
  - `taskQueue.push` 改为锁内判定 `closed → ctx → deadline → 空间/ErrPoolFull`，
    并从 `select` 回到循环顶部重判。
- 关键不变量与时序：
  - 被拒绝的提交不改变 `queue.taskNum`、不创建 worker、不做 pending 记账；
  - `closed` 一旦在锁内置位，任何后续 push 都返回 `ErrPoolClosed`，与 ctx/deadline 无关；
  - `woke` 的 `notFull` 归还只在"消费了空位提示但最终因 ctx/deadline 未入队"时发生；
    因 closed 返回时不需要归还（`closedCh` 广播会唤醒所有等待者）；
  - `ctx.Err()` 在 `queue.mu` 外读取，避免用户自定义 Context 的方法在锁内执行；
    因此"读取后、加锁前"取消的任务仍可能入队，由 dispatcher/worker 的 `abortErr` 跳过。

#### T3（已完成）

- 设计决策：
  - **结果分类与记账分离**：`runTask` 只负责产生 `taskOutcome`（completed/error/
    panic/canceled/deadline-skipped），`finishTask` 是所有终态的唯一入口。它先
    `pending.done()`，再做 panic 日志等副作用，保证 logger/hook 异常不绕过记账。
  - **接受与 +1 原子化**：pending 只在"任务已写入 chunk"的同一临界区（`pushLocked`
    内回调 `onAccept`）增加。因此拒绝路径天然不记账，也不会出现"dispatcher 先 pop
    扣账、提交方才 +1"的负计数窗口。实现初期曾把 +1 放在 `Submit` 入口，
    `TestPendingExcludesBlockedSubmit` 暴露了它与 T0 第 1 条冲突，随后改为当前方案。
  - **dispatcher 两条丢弃路径统一**：pop 后立即发现取消/超期、以及等 worker 期间
    发现取消/超期，都走 `outcomeForAbort + finishTask`，不再静默 `continue`/`return`。
  - **可重建 drain channel**：`pendingTracker` 在 0→1 时换新 channel、减到 0 时关闭，
    支持多批次等待；T3 只做内部实现，公开 `WaitIdle` 留给 T4。
- API/内部结构变化：

#### T4（已完成）

- 设计决策：
  - **两组计数、一个等待条件**：`pendingTracker` 增加 `submitting`，`wait` 以
    `pending+submitting == 0` 为条件。这样 `WaitIdle` 覆盖“已接受 + 正在提交”，
    而 `Pending()` 的未来语义仍然只统计已接受任务（3.5 第 1 条）。
    T4 开始前该冲突已向你确认，选择“新增独立计数”而不是改 pending 定义。
  - **提交中从 `enqueue` 起算**：`beginSubmit` 在 `push` 之前、`endSubmit` 在 `push`
    返回之后（含被拒绝）。因此一个阻塞在满队列上的 `Submit` 会让 `WaitIdle` 等待，
    而不会出现“WaitIdle 返回后任务才开始执行”的空窗。
  - **批次快照 + 可重建 channel**：等待者持有调用时刻的 `idle` channel；总数减到 0
    时关闭，唤醒这一批；之后的新任务换新 channel，属于下一批。多个等待者共享同一
    批次；同一 tracker 支持多批“提交 → 等待 → 再提交”。
  - **不关闭池、不等 goroutine 退出**：`WaitIdle` 只等待任务终态；`WaitPool` 仍负责
    等 dispatcher/worker 退出，两者职责分离（4.3）。
- API/内部结构变化：
  - `pendingTracker`：`n` 拆成 `pending`/`submitting`，新增 `beginSubmit`、
    `endSubmit`、`submittingSnapshot`、`totalLocked`/`beginLocked`/`endLocked`；
  - `enqueue` 增加 `beginSubmit` + `defer endSubmit`；
  - `WaitIdle` 接入 `p.pending.wait()`，补齐文档语义与“不要在任务内调用”的警告；
  - 公开签名不变。
- 关键不变量与时序：
  - `pending` 与 `submitting` 的增减都在 `pending.mu` 内；两者之和归零时恰好关闭一次
    当前 `idle` channel；
  - 锁顺序仍为 `queue.mu → pending.mu`（`add` 在 `q.mu` 内；`begin/endSubmit` 在
    `q.mu` 外）；
  - `WaitIdle` 返回时，调用时刻的“已接受 + 提交中”批次已经归零；新批次不保证被覆盖；
  - `Close → WaitIdle → WaitPool` 是受支持的关闭顺序。

    `-race -count=10`（含 100k 压测）、`-race` 下 T4 测试 `-count=20`、
