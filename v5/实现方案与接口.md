## 2. 总体架构

```text
Submit / SubmitCtx / SubmitBefore
        │  Submit:          ctx = Background, 无 deadline
        │  SubmitCtx:       允许 ctx 在等待空间时取消；nil ctx 视为 Background
        │  SubmitBefore:    deadline = now + timeout，"开始执行"期限
        ▼
taskQueue（queue.mu 保护）
  chunk FIFO：head ──► … ──► tail
  每个 chunk 预分配 tasks[MaxChunkLen]；count/read 记录块内状态
  消费完的 chunk 进入 recycled 复用缓存（上限 4096 槽，T9）
  notEmpty 只在空→非空时发送；notFull 只在 pushers>0 时发送（T9）
  notEmpty / notFull / closedCh 只做唤醒提示
        │ pop()（唯一消费者）
        ▼
dispatcher goroutine
  · 队列空且未关闭 → 阻塞在 queue.pop
  · pop 到任务后先 abortErr()，已取消/超期则 finishTask(t, skipped) 丢弃
  · idle 容器非空 → Pop 一个 worker，send 一个任务（默认 FIFO，T12）
  · running < Capacity → makeWorker(firstTask) 新建 worker
  · 否则 select 等待 workerFree / task ctx.Done / deadline timer；
    取消或超期则 finishTask(t, skipped) 丢弃，继续 pop 下一个任务（T5）
        ▼
worker goroutine
  tasks chan（cap=1）
  循环：runTask(t)（Started → Fn）→ finishTask(t, outcome)（记账 → 诊断/hook）
        → pushBack(wk)（放回 idle 容器尾部）→ 等下一个任务 / idle timeout / drained
```

观测点（T6，全部同步执行，不另起 goroutine）：

```text
Submitted  ← enqueue（提交者 goroutine；入队尝试前）
Enqueued   ← enqueue（提交者 goroutine；push 成功、queue.mu 释放后）
Started    ← runTask（worker goroutine；abortErr 通过后、Fn 前）
Completed  ← finishTask → observeOutcome（worker；pending 扣减后；不含 skipped）
Skipped    ← finishTask → observeOutcome（dispatcher 或 worker；canceled/deadline）
PoolClosed ← Close（Close 调用者；queue.close 后，恰好一次）
```

指标读取（T7）：`Pending` 与 5 个累计计数走 `pendingTracker.mu`；`Queued` 走
`queue.mu`；`Running/Idle/Busy/WorkerCreateCount` 走 `p.mu`；`Capacity` 读取不可变配置。

职责划分：

| 部件 | 职责 | 不负责 |
|---|---|---|
| submitter | 构造 `task`、检查入参、在队列满时阻塞或快速失败 | 不决定任务是否执行 |
| `taskQueue` | 保存已接受任务，维护 FIFO、长度上限、关闭状态与 chunk 复用；接受任务时回调 `onAccept` | 不执行任务、不维护 pending 计数 |
| dispatcher | 唯一消费者；从 idle 认领 worker 或按需新建；丢弃取消/超期任务并 `finishTask`（触发 Skipped）；等 worker 时也响应取消/期限（T5） | 不执行任务、不回收 idle（worker 自己回收） |
| worker | 执行 `runTask`、触发 Started、recover panic、`finishTask` 后放回 idle 容器 | 不改变队列状态、不直接操作 pending |

`Pool.pending` 是唯一的 pending 计数者；`taskQueue` 只在“任务已写入 chunk”的同一临界区
回调 `onAccept`，让“接受”与“pending +1”原子化（第 6.1 节）。

`finishTask` 是终态的唯一入口：先 `pending.done()`，再由 `observeOutcome` 依次执行
error/panic 诊断与 Completed/Skipped hook。所有回调都发生在记账之后，且不持有
`p.mu` / `queue.mu`（7.3）。

与上游 `reference-agilePool` 的关系：

- 参考点：任务缓冲、idle worker 复用、按需扩容、idle timeout 缩容、后续 hook/metrics 能力。
- 主动保留的不同：`TaskFunc` 显式携带 `ctx`；`Submit` 返回错误而不是静默丢弃；
  dispatcher 单消费者 + 包内 `idleContainer`（默认 FIFO 双向链表），而不是 worker
  自己从共享队列拉取；
  `WaitGroup` 按 worker 计数而非按任务计数；`WaitPool` 要求先 `Close`。
  上游为 idle 提供 LIFO/FIFO/ring 多种容器；这里在包内提供两种实现（默认 FIFO
  双向链表、对照 LIFO 栈），不暴露到公开 API（T12）。
- 这些差异是 v4/v5 已确定的设计，不因为"上游不是这样"而改。

## 3. 任务状态机与所有权（当前行为）

### 3.1 状态转移

| 状态 | 进入条件 | 持有者 | 离开路径 |
|---|---|---|---|
| S0 提交中 | 调用 `Submit*` | submitter | 拒绝（见 3.2）或入队 → S1 |
| S1 排队中 | `queue.pushLocked` 成功 | `queue.mu` 保护的 chunk | dispatcher `pop` → S2；Close 后仍会被 pop |
| S2 dispatcher 持有 | `queue.pop` 返回 | dispatcher 的局部变量 `t` | `abortErr` 非空（pop 时或等 worker 期间）→ `finishTask` 终态；否则认领 worker → S3 |
| S3 已认领、待交接 | 从 idle 取走 worker 或 `makeWorker(firstTask)` | worker 的 `tasks` channel（cap=1） | worker 收到 → S4 |
| S4 执行中 | `runTask` 开始 | worker goroutine 栈 | `runTask` 返回 outcome → `finishTask` → 终态 |
| S5 终态 | 见 3.3 | 无 | — |

### 3.2 拒绝路径（任务从未入队）

- `SubmitCtx` 的 ctx 在入队前已取消 → 返回 `context.Canceled`。
- `SubmitBefore` 的 deadline 在入队前已过（含 `timeout <= 0`）→ 返回 `context.DeadlineExceeded`。
- 队列已关闭 → 返回 `ErrPoolClosed`。
- `Mode == NONBLOCK` 且队列已满 → 返回 `ErrPoolFull`。
- `fn == nil` → 返回 `ErrNilTask`（T2 起）：任务不会入队，也不会启动 worker；
  该检查先于 ctx、池关闭和 timeout 判断。

拒绝路径不占 pending（T3 之后同样不应增加 pending）。

### 3.3 终态（当前实现）

| 终态 | 触发点 | T3 内部表示 | 当前可观测性（T6） |
|---|---|---|---|
| completed | `Fn` 返回 `nil` | `TaskCompleted` | `Completed` hook（`outcome.Result`） |
| returned error | `Fn` 返回非 nil | `TaskFailed`，error 保存在 `outcome.err` | `ErrorHandler` + `Completed(TaskFailed)` |
| panic | `Fn` panic | `TaskPanicked`，recover 值保存在 `panicVal`；stack 在 recover 点捕获 | `PanicHandler`（未配置则默认 Logger 输出含 stack）+ `Completed(TaskPanicked)` |
| canceled skipped | S2 的 `abortErr` 或 S4 入口检查 | `TaskCanceled` | `Skipped(TaskCanceled)`；不触发 Started/Completed |
| deadline skipped | 同上 | `TaskDeadlineSkipped` | `Skipped(TaskDeadlineSkipped)`；不触发 Started/Completed |

### 3.4 所有权与 pending 记账（T3 起）

| 阶段 | 谁拥有 task | 谁负责 pending |
|---|---|---|
| S0 提交中 | submitter 栈 | 不增加；`push` 被拒绝时也不记账 |
| S1 排队中 | `taskQueue`（`queue.mu`） | 接受时在 `queue.mu` 内回调 `onAccept` → `pending.add()` |
| S2 dispatcher 持有 | dispatcher 栈 | 丢弃时 `finishTask(t, outcomeForAbort(...))` → `pending.done()` |
| S3/S4 worker 持有 | worker / `runTask` 栈 | `finishTask(t, runTask(t))` → `pending.done()` |
| S5 终态 | 无 | — |

“恰好一次”依赖所有权转移，而不是额外的去重结构：

- `push` 成功 → 所有权归队列；dispatcher 是唯一 `pop` 者，pop 后要么 `finishTask`，
  要么交给 worker；
- 交给 worker 后，`runTask` 必定返回一个 `taskOutcome`，worker 随即 `finishTask`；
- dispatcher 的丢弃分支与交接分支互斥，不存在“既丢弃又发送”；
- worker 的 `drained` 分支收到的最后一个任务同样走 `finishTask(runTask(t))`；
- dispatcher 只在“队列已关闭且为空”时退出，因此不会留下无人认领的已接受任务。

重复扣减会把计数减成负数，测试以 `pending != 0` 兜底（见 `TestPending*`）。

S0 的“正在提交”不计入 pending，但由 `submitting` 记录，供 `WaitIdle` 等待（T4）：
`enqueue` 在 `push` 前 `beginSubmit`、返回后 `endSubmit`。因此 `WaitIdle` 不会在
提交者仍阻塞于满队列时提前返回，而 `Pending()` 指标的语义保持不变。

### 3.5 已确认语义（T0，2026-11-22 确认）

1. `pending` 只统计**已接受**（已入队/已派发）任务，S0 中尚未入队的提交不计入。
2. 终态固定为 `completed / returned error / panic / canceled skipped / deadline skipped`；
   `Completed` hook 不覆盖 skipped 任务，skipped 单列。
3. 普通任务返回的 error 只做回调 + 计数，**不自动重试**；重试只属于 T10 的 `TaskWithRetry`。
4. `Running` 保持"存活 worker（含 idle）"语义；`Busy` 另设，不改变 `Running`。
5. `Close` 后 `WaitIdle` 仍可等待已接受任务归零；`WaitPool` 仍要求先 `Close`。
6. `fn == nil` → `ErrNilTask`（T2 已实现），与"提交失败不增加 pending、不影响后续任务"一致。

## 4. 公开 API

以下是当前代码的**准确签名**（`pool_interface.go`、`observability.go`、`metrics.go`）：

```go
func New(cfg Config) (*Pool, error)

func (p *Pool) Submit(fn TaskFunc) error
func (p *Pool) SubmitCtx(ctx context.Context, fn TaskFunc) error
func (p *Pool) SubmitBefore(fn TaskFunc, timeout time.Duration) error

func (p *Pool) Close()
func (p *Pool) WaitPool()
func (p *Pool) WaitIdle()

// T7 指标
func (p *Pool) Pending() int
func (p *Pool) Queued() int
func (p *Pool) Running() int
func (p *Pool) Idle() int
func (p *Pool) Busy() int
func (p *Pool) Capacity() int
func (p *Pool) WorkerCreateCount() int64
func (p *Pool) Submitted() int64
func (p *Pool) Rejected() int64
func (p *Pool) Completed() int64
func (p *Pool) Dropped() int64
func (p *Pool) Panicked() int64

type TaskFunc func(ctx context.Context) error

type BlockMode int
const (
	BLOCK BlockMode = iota
	NONBLOCK
)

type Config struct {
	Capacity     int
	IdleTimeout  time.Duration
	MaxChunkLen  int
	MaxBuffered  int
	Mode         BlockMode

	Logger       Logger
	ErrorHandler ErrorHandler
	PanicHandler PanicHandler
	Hooks        Hooks
}

type Logger interface {
	Printf(format string, args ...any)
}

type ErrorHandler func(ctx context.Context, err error)
type PanicHandler func(ctx context.Context, recovered any, stack []byte)

type TaskResult int
const (
	TaskCompleted TaskResult = iota // Fn 返回 nil
	TaskFailed                      // Fn 返回非 nil error
	TaskPanicked                    // Fn panic，已隔离
	TaskCanceled                    // 执行前 ctx 已取消
	TaskDeadlineSkipped             // 执行前已过 SubmitBefore 期限
)
func (r TaskResult) String() string

type TaskOutcome struct {
	Result TaskResult
	Err    error // 仅 TaskFailed
	Panic  any   // 仅 TaskPanicked
}

type Hooks struct {
	Submitted  func(ctx context.Context)
	Enqueued   func(ctx context.Context)
	Started    func(ctx context.Context)
	Completed  func(ctx context.Context, outcome TaskOutcome)
	Skipped    func(ctx context.Context, outcome TaskOutcome)
	PoolClosed func()
}

var (
	ErrPoolClosed     = errors.New("pool: closed")
	ErrPoolFull       = errors.New("pool: task buffer full")
	ErrNilTask        = errors.New("pool: nil task")

```

### 4.1 提交接口的区别

| 接口 | 任务 ctx | deadline | 队列满（BLOCK） | 队列满（NONBLOCK） |
|---|---|---|---|---|
| `Submit` | `context.Background()` | 无 | 阻塞直到有空位/关闭 | `ErrPoolFull` |
| `SubmitCtx` | 调用者提供（nil 视为 Background） | 无 | 阻塞，但可被 ctx 取消 | `ErrPoolFull` |
| `SubmitBefore` | `context.Background()` | `now + timeout` | 阻塞，可被 deadline 打断 | `ErrPoolFull` |

三者的共同语义：

- 返回 `nil` **只表示"已接受并入队"**，不表示已经执行，也不表示一定执行
  （之后仍可能因 ctx 取消或 deadline 过期被跳过）。
- 返回错误时任务没有入队，也没有启动任何执行。
- `fn == nil` 在三个接口上都返回 `ErrNilTask`，不会入队，也不会依赖 worker recover 才发现。

### 4.2 `SubmitBefore` 的两层语义

`timeout` 是"**开始执行**的最后期限"，不是"执行时长上限"：

1. 在等待队列空位时超时 → 返回 `context.DeadlineExceeded`，任务不入队。
2. 已入队但在出队、等 worker 或开始执行之前过期 → 任务被跳过，不执行 `Fn`。
   T5 起，dispatcher 等 worker 的 `select` 也会监听 deadline，不必等 worker 释放才跳过。
3. 已经交给 `Fn` 之后，池子不会因为 deadline 到期而中断它；`Fn` 拿到的 ctx 是
   `context.Background()`，需要时由调用者自己用 `SubmitCtx` 控制。

`timeout <= 0` 属于调用方参数错误：立即返回 `context.DeadlineExceeded`，不进入队列等待，
也不看池状态（这是第 4.5 节优先级里的唯一例外，测试
`TestNonPositiveTimeoutIsArgumentError` 固定了这一点）。

### 4.3 关闭与等待

- `Close()`：幂等；停止接收新任务，已接受任务继续由 dispatcher 排空。它不等待任务
  完成，但会同步触发 `PoolClosed` hook——阻塞的 hook 会延长 `Close` 的返回时间。
  并发 `Close` 由 `sync.Once` + `queue.closed` 双重保护。
- `WaitPool()`：等待 dispatcher 和所有 worker 退出；**必须在 `Close()` 之后调用**，
  否则 dispatcher 会一直等队列，`WaitPool` 不会返回。Wait 返回后重复调用会立即返回。
- `WaitIdle()`：等待“已接受 + 正在提交”的任务全部到达终态，但不关闭池。
  空池立即返回；不需要先 `Close`；多个 goroutine 可以同时等待；一批完成后可以再次
  等待下一批。等待范围包含阻塞在满队列上的 `Submit`（`submitting` 计数），但 `pending`
  指标本身仍只统计已接受任务（T0 第 1 条）。它是“批次快照”语义：等待期间新提交的
  任务属于下一批，不保证被本次 `WaitIdle` 覆盖。`Close` 之后仍可调用，用于等待已接受
  任务排空；池退出等待仍用 `Close + WaitPool`。不要从任务函数内部调用 `WaitIdle`
  （任务自己也是 pending，会等自己造成永久阻塞）。
- `Running()`：当前存活 worker 数，包含 idle worker，不包含 dispatcher。

### 4.4 最小示例

```go
p, err := pool.New(pool.Config{
	Capacity:    4,
	IdleTimeout: time.Second,
	MaxChunkLen: 64,
	MaxBuffered: 1024,
	Mode:        pool.BLOCK,
})
if err != nil {
	return err
}

if err := p.Submit(func(ctx context.Context) error {
	// 任务逻辑；返回 error 会交给可选的 ErrorHandler（4.6）
	return nil
}); err != nil {
	// nil 只表示已入队；这里拿到的是拒绝原因
	return err
}

p.Close()    // 停止接收，dispatcher 开始排空
p.WaitPool() // 等 dispatcher 与所有 worker 退出
```

### 4.5 提交错误优先级（T2 固定）

| 优先级 | 条件 | 返回 |
|---|---|---|
| 1 | `fn == nil` | `ErrNilTask` |
| 2 | `SubmitBefore` 且 `timeout <= 0` | `context.DeadlineExceeded` |
| 3 | 队列已关闭（`Close` 之后） | `ErrPoolClosed` |
| 4 | 任务 ctx 已取消/已到期 | `ctx.Err()` |
| 5 | 任务 deadline 已过（等待空间期间） | `context.DeadlineExceeded` |
| 6 | `NONBLOCK` 且队列满 | `ErrPoolFull` |

为什么这样排：

- 1–2 是参数错误，不依赖池状态，先于任何状态判断；
- 3 是池的终态：`Close` 之后所有提交稳定返回 `ErrPoolClosed`，producer 循环不需要
  再区分"是关闭还是恰好 ctx 取消"；
- 4–5 是任务级运行时条件，按"先 ctx 后 deadline"排序；
- 6 只在队列确实满且调用方选择 `NONBLOCK` 时出现。

实现位置：1–2 在 `Submit / SubmitCtx / SubmitBefore` 入口完成；3→4→5→6 在
`taskQueue.push` 的 `queue.mu` 内判定。`push` 从 `select` 醒来后不直接返回，
而是回到循环顶部重新判定，保证关闭与取消同时发生时仍按上表返回。

### 4.6 错误、panic 与生命周期 hook（T6）

`Config` 的 4 个可选字段全部在 `New` 时固定，运行期间不可替换：

| 字段 | 类型 | 触发条件 | nil 行为 |
|---|---|---|---|
| `Logger` | `Logger`（`Printf`） | 默认 panic 报告、回调自身 panic | 回退 `log.Default()` |
| `ErrorHandler` | `func(ctx, error)` | `Fn` 返回非 nil error | 静默丢弃 error |
| `PanicHandler` | `func(ctx, recovered, stack)` | `Fn` panic 被 recover | 通过 Logger 输出默认报告（含 stack） |
| `Hooks` | `Hooks` 结构体 | 6 个生命周期事件 | 对应字段为 nil 时不调用 |

`Hooks` 的触发语义：

| 回调 | goroutine | 时机 | 覆盖范围 / 次数 |
|---|---|---|---|
| `Submitted` | submitter | `enqueue` 内、`beginSubmit` 后、`push` 前 | 每次合法提交尝试（含随后被拒绝）恰好一次 |
| `Enqueued` | submitter | `push` 成功、`endSubmit` 后（`queue.mu` 已释放） | 每个被接受任务恰好一次 |
| `Started` | worker | `abortErr` 通过后、`Fn` 前 | 实际执行的任务；被跳过任务不触发 |
| `Completed` | worker | `finishTask` 内，`pending.done` 后 | completed / error / panic；每个执行任务一次 |
| `Skipped` | dispatcher 或 worker | 同上 | canceled / deadline-skipped；与 Completed 互斥 |
| `PoolClosed` | Close 调用者 | `queue.close` 后、`Close` 返回前 | 整个池一次（并发 Close 也只一次） |

通用规则：

- 回调同步执行、不另起 goroutine，也不在 `p.mu` / `queue.mu` 内执行；
- 回调 panic 被 `recover` 隔离，并通过 Logger 记录 stack；Logger 自身 panic 也被吞掉；
- 同一任务：`Submitted → Enqueued`、`Started → Completed` 的顺序成立；
  `Enqueued` 与 `Started` 不保证顺序（任务入队后可能立刻被 dispatcher 取走并执行）；
- 所有 hook 都不在 `WaitIdle` 的等待条件内：`Completed` / `Skipped` 在 `pending.done()`
  之后执行，`Enqueued` 也可能晚于 `WaitIdle` 返回；
- 不同任务的回调可能并发，回调实现需要自行同步；不要长时间阻塞，也不要重入
  `Submit` / `WaitIdle` / `WaitPool` / `Close`（原因见 `Hooks` 的代码文档）。

`TaskOutcome` 是只读快照：`Result` 五选一，`Err` 只在 `TaskFailed` 时非 nil，
`Panic` 只在 `TaskPanicked` 时非 nil。panic 的 stack 不放进 `TaskOutcome`，只传给
`PanicHandler` 或默认日志。

### 4.7 观测配置示例

```go
p, err := pool.New(pool.Config{
	Capacity:    4,
	IdleTimeout: time.Second,
	MaxChunkLen: 64,
	MaxBuffered: 1024,
	Mode:        pool.BLOCK,

	Logger: log.Default(),
	ErrorHandler: func(ctx context.Context, err error) {
		log.Printf("task failed: %v", err)
	},
	PanicHandler: func(ctx context.Context, recovered any, stack []byte) {
		log.Printf("task panic: %v\n%s", recovered, stack) // stack 已格式化为文本
	},
	Hooks: pool.Hooks{
		Submitted: func(ctx context.Context) { /* 提交计数 */ },
		Completed: func(ctx context.Context, out pool.TaskOutcome) {
			if out.Result == pool.TaskFailed {
				/* 已由 ErrorHandler 报告；这里可做统计 */
			}
		},
		Skipped: func(ctx context.Context, out pool.TaskOutcome) {
			/* out.Result 为 TaskCanceled 或 TaskDeadlineSkipped */
		},
		PoolClosed: func() { /* 停止提交后的收尾通知 */ },
	},
})
```

示例中的 `ctx` 来自提交任务；`Submit` / `SubmitBefore` 的任务是 `context.Background()`，
需要携带关联信息时使用 `SubmitCtx`（见 7.5）。

### 4.8 运行指标（T7）

所有指标都是一次独立瞬时快照；不同方法之间不保证来自同一时刻。

| 方法 | 类型 | 含义 |
|---|---|---|
| `Pending()` | `int` | 已接受（已入队/已派发）、未到终态的任务数；不含提交中 |
| `Queued()` | `int` | 缓冲队列中的任务数；不含 dispatcher 持有与执行中 |
| `Running()` | `int` | 存活 worker 数（含 idle） |
| `Idle()` | `int` | idle 容器中的 worker 数 |
| `Busy()` | `int` | `running - len(idle)`：已认领/交接/执行中 |
| `Capacity()` | `int` | 配置的 worker 上限 |
| `WorkerCreateCount()` | `int64` | 自 `New` 以来创建过的 worker 总数（单调） |
| `Submitted()` | `int64` | 进入 enqueue 的合法提交尝试数 |
| `Rejected()` | `int64` | Submitted 中未能入队的数量 |
| `Completed()` | `int64` | completed/error/panic 终态任务数 |
| `Dropped()` | `int64` | 已接受但取消/超期被跳过的任务数 |
| `Panicked()` | `int64` | panic 次数（Completed 的子集） |

使用规则：

- 每个方法只获取一把内部锁（`Capacity` 无锁）；不会为了“组合快照”同时持有多把锁。
  需要多个值时请接受它们可能来自不同时刻，不要用它们做跨指标恒等式断言。
- `Busy()` 在单次调用内满足 `Idle()+Busy()==Running()`（同一 `p.mu` 快照）；
  但它可能短暂包含刚执行完、尚未 `pushBack` 或刚 `removeIdle` 尚未 `running--` 的 worker。
- 关闭并 `WaitPool` 后，`Pending/Queued/Running/Idle/Busy` 均为 0；`Capacity` 不变，
  `WorkerCreateCount` 与 5 个累计计数不回落。
- 约定恒等式（所有已接受任务都终态、且没有正在 Submit 的调用时）：
  `Submitted = Rejected + Completed + Dropped`。
  当仍有提交阻塞在 `push` 或任务在途时，两边相差正在提交/尚未终态的任务。
- 参数错误（`nil` task、`SubmitBefore` 的非正 timeout）不进入 enqueue：不计入
  `Submitted`/`Rejected`，也不触发 hook。
- 累计计数与 T6 hook 对齐：`Submitted` ↔ Submitted hook；`Dropped` ↔ Skipped hook；
  `Completed` 覆盖 Completed hook 的三类结果；`Panicked` 是其中 panic 的子集。

最小读取示例：

```go
p.WaitIdle()
fmt.Printf("pending=%d queued=%d running=%d idle=%d busy=%d capacity=%d created=%d\n",
	p.Pending(), p.Queued(), p.Running(), p.Idle(), p.Busy(), p.Capacity(), p.WorkerCreateCount())
fmt.Printf("submitted=%d rejected=%d completed=%d dropped=%d panicked=%d\n",
	p.Submitted(), p.Rejected(), p.Completed(), p.Dropped(), p.Panicked())
```

`Completed` 包含 error 与 panic；需要区分具体终态时使用 T6 的 `Completed` hook 与
`TaskOutcome.Result`。

## 5. Config 配置说明

| 字段 | 默认值 / 零值行为 | 合法范围 | 说明 |
|---|---|---|---|
| `Capacity` | 无默认；`<= 0` 时 `New` 返回 error | `> 0` | worker 数量上限，也是并发执行上限 |
| `IdleTimeout` | `<= 0` → `1s` | 任意时长 | worker 空闲多久后退出；退出后容量槽释放 |
| `MaxChunkLen` | `<= 0` → `64` | `> 0` 才有效 | 每个 chunk 预分配的任务槽数 |
| `MaxBuffered` | `0` → `MaxChunkLen`；`-1` 不设限 | `-1` 或 `>= 1`；`< -1` 返回 error | **只限制队列中任务数**，不含执行中任务与 dispatcher 持有的任务 |
| `Mode` | 无默认 | `BLOCK` / `NONBLOCK` | 队列满时阻塞提交还是返回 `ErrPoolFull` |
| `Logger` | `nil` → `log.Default()` | 任意 `Logger` 实现 | 池诊断输出；构造期固定，运行期只读 |
| `ErrorHandler` | `nil` → 不回调 | `func(ctx, error)` | 只接收 `Fn` 返回的 error，不影响任务语义 |
| `PanicHandler` | `nil` → 默认日志 | `func(ctx, any, []byte)` | 配置后替代默认 panic 日志，stack 来自 recover 点 |
| `Hooks` | 零值 → 不回调 | `Hooks` 结构体 | 6 个生命周期回调；构造期固定 |

关系：

- `MaxBuffered` 不必是 `MaxChunkLen` 的倍数；队列按 chunk 链增长，
  实际占用约 `ceil(MaxBuffered/MaxChunkLen)` 个 chunk。
- 消费完的 chunk 最多保留 `maxRecycledSlots = 4096` 个任务槽位用于复用
  （T9）；`MaxChunkLen > 4096` 时不缓存。recycled 块不在队列中，不占 `taskNum`，
  也不计入 `MaxBuffered`。
- `Capacity` 与 `MaxBuffered` 相互独立：前者限制"同时执行"，后者限制"排队"。
- `MaxBuffered = 0` 被解释为"一个 chunk"，不是"零缓冲"；当前实现没有"零缓冲"配置，
  最小缓冲就是一个 chunk。需要"队列满时快速失败"请用 `NONBLOCK`，而不是把
  `MaxBuffered` 设成 0。
- 配置的默认值与校验集中在 `normalizeConfig`（由 `New` 调用）；非法组合返回 error，
  不会启动 goroutine。

## 6. 核心并发不变量

### 6.1 锁、channel 与计数

| 对象 | 保护/含义 | 只在哪里修改 |
|---|---|---|
| `p.mu` | 保护 `p.idle`（`idleContainer`）、`p.running`、`p.created` | 所有 idle 增删、running 加减、worker 创建计数 +1 |
| `queue.mu` | 保护 `head/tail/taskNum/closed`、chunk 的 `tasks/next/read/count`、`pushers` 与 `recycled` | `pushLocked`、`popLocked`、`close`、`size` |
| `q.notEmpty`（cap=1） | "队列可能非空"的提示；只在空→非空时发送 | `signalNotEmpty`（`push`） |
| `q.notFull`（cap=1） | "队列可能有空位"的提示；只在 `pushers > 0` 时发送 | `push` / `pop` / `forwardNotFull` |
| `q.pushers` | 已被判定为满、正在 `notFull` 上等待的 BLOCK 提交者数 | 在“锁内判定为满”的同一临界区 +1；`select` 醒来后 -1 |
| `q.recycled` | 已消费完、可复用的 chunk（上限 `maxRecycledSlots` 个槽位） | `popLocked` 回收；`pushLocked` 取用；`close` 清空 |
| `q.closedCh` | 队列关闭广播 | `queue.close` 中 `close` 一次 |
| `p.workerFree`（cap=1） | "可能有 idle worker 或容量槽释放"的提示；只是提示，dispatcher 醒来后必须在 `p.mu` 内复查 | `pushBack`、`decRunning` |
| `p.drained` | dispatcher 排空并退出后关闭 | dispatcher 的 defer |
| `p.wg` | dispatcher 1 + 每个 worker 1；**不按任务计数** | `New`、`makeWorker`、goroutine 退出 |
| `p.onceClose` | `Close` 幂等 | `Close` |
| `p.logger` / `p.hooks` / `p.errorHandler` / `p.panicHandler` | 构造期固定，运行期只读；不需要锁或原子操作 | 只在 `New` 写入 |
| `p.pending.mu` | 保护 `pending`/`submitting` 实时计数、五个累计计数（`submitted/rejected/completed/dropped/panicked`）与可重建的 drain channel；等待条件是实时计数之和为 0 | `add`（仅在 `queue.mu` 内回调）、`done(result)`（`finishTask`）、`beginSubmit`/`endSubmit(accepted)`（`enqueue`）、`wait`/`snapshot`/`counters` |

所有提示 channel 都允许"提示过期"：等待者醒来后必须在锁内重新检查真实条件，
不能假设"收到信号就一定有空间/worker"。

T5 起，dispatcher 等 worker 时除了 `workerFree` 还监听两个真实事件：任务 ctx 的
`Done`（取消或 ctx 自身到期）和 `SubmitBefore` 的 deadline timer。它们的就绪就是
"任务不该再执行"的结论，不再需要回锁复查；醒来后直接走统一终态入口（6.5）。

锁顺序固定为 `queue.mu → pending.mu`：`pushLocked` 在持有 `queue.mu` 时回调 `onAccept`
→ `pending.add`；`finishTask` 只获取 `pending.mu`，不获取 `queue.mu`，因此不存在反向
锁环。`beginSubmit`/`endSubmit` 在 `queue.mu` 之外获取 `pending.mu`，同样不反向持有
`queue.mu`。用户任务、Logger、ErrorHandler、PanicHandler 与生命周期 hook 都不在
`p.mu` / `queue.mu` 内执行（6.6 有逐项说明）。

### 6.2 worker 交接保证

1. dispatcher 从 `p.idle` 取走一个 worker 后，**必须向它的 `tasks` send 恰好一个任务**；
   中途取消也不能改发"跳过信令"或直接放弃，否则 `Close` 路径里阻塞的
   `t = <-wk.tasks` 会永久等不到任务。
2. `makeWorker(firstTask)` 用 `firstTask` 启动，**不能再 send 一次**，否则重复执行。
3. worker 的 idle timeout 与 dispatcher 认领同时发生时，`removeIdle` 返回 `false`
   说明它已被认领；worker 必须回到 `select` 继续等任务，不能直接退出。
4. worker 收到 `drained` 时先 `removeIdle`：返回 `true` 才能退出；返回 `false`
   说明已被认领，此时 dispatcher 一定会在 `close(p.drained)` 之前完成 send，
   所以可以安全地 `t = <-wk.tasks` 收下最后一个任务并执行。
5. 任务在 S3/S4 期间被取消时，由 `runTask` 的 `abortErr` 跳过执行，worker 仍会被
   占用一次"检查"；这是语义上可接受的。T5 只优化 S2 的等待，不改变 S3/S4 的交接。
6. 被接受的任务必须且只能经过一次 `finishTask`：S2 丢弃（pop 时或等 worker 期间）、
   S3/S4 执行、worker 的 `drained` 分支各调用一次；不存在"队列里还有任务但 dispatcher
   已退出"的路径。
7. S2 的等待是 `select { workerFree, task ctx.Done, deadline timer }`：取消/超期在
   **取 worker 之前**返回并 `finishTask`，所以不会出现"已认领 worker 却没有任务可发"；
   `workerFree` 分支只是回到循环顶部复查（6.5）。

### 6.3 Close / Wait 的顺序

- `Close` 先 `queue.close`（锁内置 `closed=true`，再关 `closedCh`），此后 `push` 必然
  失败，不存在"dispatcher 已退出但队列还能成功入队"的窗口。
- `PoolClosed` 在 `queue.close` 之后、`Close` 返回之前同步触发；它不等待任务排空，
  也不改变 `WaitPool` 的语义。
- `push` 的错误优先级在锁内判定：`closed` > `ctx.Err()` > deadline > `ErrPoolFull`。
  因此 `Close` 后即使任务的 ctx 同时取消，提交方仍稳定收到 `ErrPoolClosed`（见 4.5）。
- dispatcher 只在"队列已关闭且为空"时退出，然后 `close(p.drained)`；
  因此 `drained` 关闭时所有已接受任务都已完成派发。
- `WaitPool` 依赖 `p.wg`：dispatcher 退出 + 所有 worker 退出。它不感知单个任务的完成，
  所以 `WaitPool` 不能替代任务级等待；任务级等待是 T4 的 `WaitIdle`。
- `Close → WaitPool` 返回时 pending 必须为 0：dispatcher 退出前已把所有任务交给
  worker，worker 退出前已执行并 `finishTask`；`TestPendingZeroAfterCloseAndWait`
  固定这一点。
- 关闭路径推荐顺序：`Close → WaitIdle → WaitPool`。`WaitIdle` 只等任务终态，不等待
  dispatcher/worker 退出；`WaitPool` 等待 goroutine 收尾。两者职责不同，
  `TestCloseWaitIdleWaitPool` 固定该组合。

### 6.4 idle worker 容器（T8/T12）

`p.idle` 的类型是包内接口 `idleContainer`，由 `p.mu` 保护，构造期选定：

| 实现 | 结构 | Add | Pop | Remove | 复用顺序 |
|---|---|---|---|---|---|
| `fifoIdle`（默认，T12） | 双向链表，节点内嵌在 worker 上 | O(1) | O(1) | O(1) | FIFO：先空闲先复用 |
| `stackIdle`（T8，对照） | slice 栈 | 均摊 O(1) | O(1) | O(n) | LIFO：最近归还先复用 |

契约（与接口注释一致）：

- 所有方法在 `p.mu` 内调用，容器自身不加锁；
- `Add` 后同一 worker 在容器中恰好一次；`Pop`/`Remove` 必须清空引用
  （链表指针或 slice 槽位）；
- `Pop` 空容器返回 nil；`Remove` 对已认领/未知 worker 返回 false；
- 容器不保存 idle 起始时间，也不负责关闭 worker：idle timeout 仍由每个 worker
  自己的 timer 驱动，到点调用 `removeIdle`。因此接口没有规划里的 `RemoveExpired`。

不变量（与 6.1、6.2 配套）：

1. 每个“存活且空闲”的 worker 在容器中恰好出现一次；
2. 被 Pop/Remove 的 worker 不再被容器引用（`idleLinked=false`、前后指针 nil /
   slice 槽位 nil）；
3. timeout 与 dispatcher 认领同时发生时，`removeIdle` 在 `p.mu` 内判定归属：
   返回 false 表示已被认领，worker 回到 select 继续等任务；返回 true 才允许退出；
4. 被 pop 的 worker 仍承担 6.2 第 1 条“必须恰好收到一个任务”的义务。

为什么从 LIFO 栈改为 FIFO 链表：T8 的 LIFO 栈在“大量 worker 同时超时”时是
O(n²)——最早空闲的 worker 在栈底，却最先超时，每次 Remove 都要扫描并搬移。
T12 实测 Capacity=10000 时容器删除约 11ms、池级 release→全部退出约 43ms。
先尝试的环形缓冲理论上队首删除 O(1)，但 timeout 顺序与队列顺序会因
`pushBack` 与 timer Reset 之间的调度窗口错位，端到端反而 252–265ms；
最终改为双向链表，Remove 不依赖顺序，池级耗时 31–34ms（9.12）。

公开语义：复用顺序（FIFO/LIFO）不在公开契约内；`Idle()`/`Busy()`/`Running()`
的定义与计数不变。T9 的队列信号与 chunk 复用见 6.8。

副作用（记录，不改变 IdleTimeout 的 per-worker 语义）：FIFO 轮转复用会重置被复用
worker 的 idle timer。持续但稀疏的负载会轮流“续命”所有 idle worker，缩容可能比
LIFO 慢；LIFO 则更容易保留一个热 worker、让其余 worker 超时。这是复用顺序的可观测
差异之一，T12 没有把它纳入公开契约。

### 6.5 dispatcher 等 worker 的等待协议（T5）

```go
select {
case <-p.workerFree:     // 有 worker 归还 / 容量槽释放：回循环顶部复查
case <-taskDone(t.ctx):  // ctx 取消或 ctx 自身到期：finishTask(canceled/deadline-skipped)
case <-deadlineC:        // SubmitBefore 的开始执行期限：finishTask(deadline-skipped)
}
```

- 三个事件分成两类：`workerFree` 只是"可能变了"的提示，醒来后必须回到循环顶部，
  在 `p.mu` 内重新检查 `idle` 与 `running`；取消/超期是真实事件，直接进入终态并返回。
- 终态原因统一由 `abortErr(t)` 判定：ctx 的 `Err()` 优先于 `t.deadline`，与
  `runTask` 入口的检查顺序一致。因此即使 `select` 在 ctx 与 deadline 同时就绪时
  随机选中一路，`taskOutcome` 也不会摇摆。
- 取消/超期分支在 **不持有 `p.mu`/`queue.mu`** 时调用 `finishTask`（`select` 之前
  已经 `Unlock`），后续 Logger/hook（T6）不会在内部锁内执行；记账仍然先于副作用。
- 这条路径在"取 worker 之前"返回，所以不会破坏 6.2 第 1 条：只有真正从 idle 取走
  worker 或 `makeWorker(firstTask)` 的路径才承担"必须恰好发一个任务"的义务。
- `deadlineTimer` 只在真正进入等待时创建，并由 `dispatchTask` 的 `defer Stop` 回收；
  立即派发的任务不分配 timer。deadline 是绝对时间，等待期间不需要 Reset。
- `Close` 不打断这个等待：已被接受的最后一个任务仍需要 worker 才能执行；worker 归还
  （`pushBack`）或退出（`decRunning`）都会发 `workerFree`，等待最终会结束。
- 带来的行为变化：取消/超期的任务不再占住 dispatcher，队列中后续任务可以提前派发；
  对应地，`pending` 扣减与 `WaitIdle` 返回都可能比 T5 之前更早（见 10.1）。

### 6.6 回调与锁（T6）

| 回调 | 执行 goroutine | 执行时的锁状态 |
|---|---|---|
| `Submitted` | submitter | 无（`pending.beginSubmit` 已返回，`push` 尚未开始） |
| `Enqueued` | submitter | 无（`push` 与 `endSubmit` 都已返回） |
| `Started` | worker | 无（`runTask` 不持有池锁） |
| `Completed` / `Skipped` | worker 或 dispatcher | 无（`finishTask` 只短暂持有 `pending.mu`，回调在 `done()` 之后） |
| `PoolClosed` | Close 调用者 | 无（`queue.close` 已返回） |

因此 `p.mu`、`queue.mu` 不会出现在用户回调的调用栈上。`TestHooksRunOutsideInternalLocks`
用“在回调里调用 `Running()` / `queue.size()`”验证：若池仍持锁，测试会超时失败。

回调 panic 由 `safeCallback` 隔离，只影响本次事件；`pending.done()` 在 `observeOutcome`
之前完成，所以 hook panic 不可能绕过记账。`WaitIdle` 不等待回调
（`TestWaitIdleDoesNotWaitForCompletionHooks`）。

### 6.7 指标读取与锁（T7）

| 指标 | 数据来源 | 获取的锁 | 说明 |
|---|---|---|---|
| `Pending()` | `pendingTracker.pending` | `pending.mu` | 已接受未终态 |
| `Submitted/Rejected/Completed/Dropped/Panicked()` | 同一组累计计数 | `pending.mu` | 每个方法各取一次锁内快照 |
| `Queued()` | `taskQueue.taskNum` | `queue.mu` | 只算队列内 |
| `Running()` | `p.running` | `p.mu` | 存活 worker |
| `Idle()` | `p.idle.Len()` | `p.mu` | idle 容器 |
| `Busy()` | `p.running - len(p.idle)` | `p.mu` | 单次快照内 `Idle+Busy==Running` |
| `WorkerCreateCount()` | `p.created` | `p.mu` | 单调 |
| `Capacity()` | `p.cfg.Capacity` | 无锁 | 不可变 |

指标读取只获取一把锁，不形成新的锁环；`Pending`/累计计数与 `finishTask` 共用
`pending.mu`，因此 T7 没有为 metrics 在任务热路径新增锁。代价是不同指标可能来自
不同时刻（4.8）。从 hook 内调用这些方法已验证不会重入死锁
（`TestMetricsCallableFromHooks`）。

### 6.8 队列信号与 chunk 复用（T9）

T9 之后 `taskQueue` 热路径的信号规则：

- **`notEmpty` 只在空 → 非空时发送**：`push` 在锁内记录 `wasEmpty`。队列原本非空时，
  pop 要么已经在处理，要么会在下一次循环里在锁内看到任务；不需要每次 push 都唤醒。
- **`notFull` 只在 `pushers > 0` 时发送**。`pushers` 是“已被判定为满、正在 select 等待”
  的 BLOCK 提交者数量，由 `queue.mu` 保护：
  - 提交者在“锁内判定为满”的**同一临界区** `pushers++`，保证 pop 不可能在
    “看到满”与“登记”之间插入并跳过信号；
  - pop 在锁内读取 `pushers`，释放任务后仅在有等待者时 `signalNotFull`；
  - 提交成功后若仍有空位且有等待者，`push` 转发 `notFull`；
  - 提交者被 ctx/deadline 唤醒但未能入队时，`forwardNotFull` 把消费到的空位提示
    转交给其他等待者，避免“取消者吞掉唤醒”。
  - 不变量：一次 pop 释放空位后，要么其他等待者看到 `pushers > 0` 而收到提示，要么
    当前等待者会在锁内看到空位；不存在“空位已释放、等待者仍在睡”的窗口。
- **`SubmitBefore` 的 timer 延迟创建**：`push` 只在首次进入“队列满、需要 select”时创建
  `time.Timer`；队列立即可写时零 timer 分配（基准见 9.11）。
- **chunk 复用**：`popLocked` 把完全消费的块放入 `recycled`（重置 `read/count/next`；
  槽位在 pop 时已置零），`pushLocked` 在需要新块时优先从 `recycled` 取。
  - 缓存上限 `maxRecycledSlots = 4096` 个任务槽位；`MaxChunkLen > 4096` 时不缓存；
  - 关闭时清空 `recycled`，关闭后不再回收（不会再有 push）；
  - 效果：有界队列稳态下 chunk 分配趋近于 0（端到端 Noop/Short/Sustained 的
    `B/op` 从 ~50 降到 0–1）；无界队列持续增长时块都仍存活，复用帮助有限（9.11）。
- **为什么不用 `sync.Pool`**：chunk 的生命周期已经完全由 `queue.mu` 保护，队列内
  free list 就能复用；没有 per-P 缓存重复、GC 清空和额外同步，内存上界也更容易解释。
  `sync.Pool` 在这里不会更好。
- **为什么不把 chunk 分配移出锁**：只有缓存未命中（启动/扩容）才分配；在锁外预分配
  会浪费，或者要在扩容路径引入“分配后重查 tail”的额外复杂度，目前没有基准支持。

T9 未覆盖的队列成本：`queue.mu` 仍是多生产者 + 单消费者的竞争点，profile 显示锁竞争
占主导（9.11）。批量消费、handoff、sharding 属于 T11/T14，不在 T9 范围。

## 7. 错误、panic、hook 与指标

### 7.1 类型与配置（T6 当前实现）

- `Config.Logger`：`Logger` 接口（`Printf`）；nil → `log.Default()`。只用于池诊断，
  不承载任务业务日志；Logger 自身 panic 被吞掉。
- `Config.ErrorHandler`：只接收 `Fn` 返回的非 nil error；nil 表示静默丢弃。
- `Config.PanicHandler`：接收 recover 值与 recover 点捕获的 stack；配置后替代默认
  panic 日志，handler 自身 panic 由 Logger 报告。
- `Config.Hooks`：`Hooks` 结构体的 6 个可选 func 字段；零值表示不监听。
- 以上字段全部在 `New` 时固定；`Pool` 内以只读字段保存，运行期不加锁、不做原子读写。

### 7.2 触发时机与顺序

| 回调 | goroutine | 触发点 | 覆盖范围 |
|---|---|---|---|
| `Submitted` | 提交者 | `enqueue` 中 `beginSubmit` 后、`push` 前 | 每次合法提交尝试（含随后被拒绝） |
| `Enqueued` | 提交者 | `push` 成功、`endSubmit` 后 | 每个被接受任务恰好一次 |
| `Started` | worker | `runTask` 的 `abortErr` 通过后、`Fn` 前 | 实际执行的任务 |
| `Completed` | worker | `finishTask` → `observeOutcome`，`pending.done()` 后 | completed / error / panic |
| `Skipped` | dispatcher 或 worker | 同上 | canceled / deadline-skipped |
| `PoolClosed` | Close 调用者 | `queue.close` 后、`Close` 返回前 | 整个池一次 |

顺序保证：

- 同一任务 `Submitted` 早于 `Enqueued`（同一提交者 goroutine，分别在 `push` 前/后）；
- 同一任务 `Started` 早于 `Completed`（同一 worker goroutine）；
- `Enqueued` 与 `Started` 不保证顺序：`Enqueued` 必须在 `queue.mu` 释放后触发，
  而此时 dispatcher 可能已经取走任务；
- `PoolClosed` 与并发中的其他回调没有全局顺序保证，它只保证 `queue.close` 已完成；
- 不同任务的回调可以并发，顺序不做保证。

### 7.3 记账、隔离与锁

- `finishTask(t, out)` 的顺序固定为 `pending.done()` → `observeOutcome(t.ctx, out)`。
  即使 ErrorHandler/PanicHandler/hook 永久阻塞或 panic，pending 也已经归零，
  `WaitIdle` 不会因为回调而永久等待；同时 `WaitIdle` 也不等待回调完成。
- `observeOutcome` 的固定顺序：先 error/panic 诊断（`ErrorHandler`、`PanicHandler`
  或默认日志），再触发 `Completed` 或 `Skipped`；两者互斥。
- 每个回调都由 `safeCallback` 包裹：`recover` 后通过 Logger 记录
  `name + panic 值 + debug.Stack()`；Logger 自身 panic 在 `logf` 内再次被吞掉。
- 回调不在 `p.mu` / `queue.mu` 内执行（6.6 有逐项说明）。
- 回调必须自行保证并发安全且快速返回；不要重入 `Submit` / `WaitIdle` / `WaitPool` /
  `Close`（原因见 4.6 与 `Hooks` 的代码文档）。
- `queue.push` 里的 `ctx.Err()` 在锁外读取：自定义 `context.Context` 的 `Err` 方法属于
  用户代码，不应在 `queue.mu` 持有期间调用；代价是“读取后、加锁前”被取消的任务仍可能
  入队，随后由 dispatcher/worker 的 `abortErr` 跳过。

### 7.4 panic 报告与 stack trace

- `runTask` 的 `defer recover()` 捕获 panic，并在同一 recover 点调用 `debug.Stack()`
  保存栈；栈展开结束后再抓，只能看到回调自身的栈。
- 配置了 `PanicHandler`：调用 `handler(ctx, recovered, stack)`，不再输出默认日志；
  handler panic 被隔离并记录。
- 未配置 `PanicHandler`：`Logger.Printf("task panic: %v\n%s", recovered, stack)`。
- `ErrorHandler` 只对应 `TaskFailed`；panic 不走 ErrorHandler，skipped 两者都不走。

### 7.5 已知限制

- 没有任务 ID：同一任务的多次事件只能用 `SubmitCtx` 的 ctx value 关联；
  `Submit`/`SubmitBefore` 的 ctx 是 Background，无法区分具体任务。
- `SubmitBefore` 的 deadline 不在 hook 的 ctx 中；需要观测 deadline 的任务请用
  `SubmitCtx` + `context.WithDeadline`。
- hook/Logger/handler 不支持运行中注册或替换；`New` 之后修改 `Config` 不影响池。
- 回调同步执行：慢回调会拖慢提交、worker 复用或 `Close`。
- `Completed`/`Skipped` 在 pending 扣减之后执行，`WaitIdle` 返回时回调可能尚未结束。
- 指标是瞬时快照：跨方法不保证同一时刻，`Busy` 可能包含极短的归还/退出窗口
  （4.8、6.7）；未提供一次性 `Metrics()` 组合快照。

### 7.6 运行指标（T7 当前实现）

- 公开方法与语义见 4.8，锁与快照规则见 6.7。
- 五个累计计数由 `pendingTracker` 在同一把锁内维护：`beginSubmit` 记 `submitted`，
  `endSubmit(false)` 记 `rejected`，`add` 增加 `pending`，`done(result)` 记
  `completed/dropped/panicked`；没有为 metrics 新增锁。
- 关闭并 `WaitPool` 后瞬时指标归零；`WorkerCreateCount` 与累计计数单调保留。
- 恒等式（所有已接受任务都终态、且没有正在提交的调用时）：
  `Submitted = Rejected + Completed + Dropped`。
- 未实现一次性组合快照：若后续需要 `Metrics()`，必须在单次调用内按固定顺序获取
  多个锁，并明确锁顺序；当前版本刻意不引入这类约束。

## 8. 重试设计（T10，尚未实现）

尚未实现，先固定以下约束，避免 T10 走偏：

- `RetryNum` 表示**额外重试次数**，总执行次数为 `RetryNum + 1`。
- 一个逻辑任务只增加一次 pending，所有尝试结束后只减少一次。
- 默认只对普通 error 重试；panic 默认不重试（需要单独定义才可重试）。
- 退避等待必须可被 ctx 取消；deadline 到期后不再发起重试。
- 不得使用不可取消的裸 `time.Sleep`。
- hook 与重试的预决策：重试属于**同一个逻辑任务**，
  `Submitted/Enqueued/Started/Completed/Skipped` 仍各触发一次；一次逻辑任务只增加
  一次 pending、只扣减一次。每次尝试的 error 是否交给 `ErrorHandler` 由 T10 定义，
  但不会因此重复触发 `Completed`。

### 9.4 端到端基准（GOMAXPROCS=12，`-benchtime=200ms`，3 次中位数）

配置均为 `Capacity=32`、`MaxChunkLen=64`、`IdleTimeout=1s`、`Mode=BLOCK`；
计时范围都包含提交、任务执行和 `Close+WaitPool` 排空；计时前预热 32 个任务。

| Benchmark | 负载 | MaxBuffered | ns/op | B/op | allocs/op | peak-queue | peak-workers |
|---|---|---|---|---|---|---|---|
| `BenchmarkEndToEndNoop` | 空任务 | 4096 | 744.4 | 66 | 0 | 4096 | 32 |
| `BenchmarkEndToEndShort` | 32 次乘加 | 4096 | 759.0 | 66 | 0 | 4096 | 32 |
| `BenchmarkEndToEndLong` | `Sleep(200µs)` | -1 | 18972 | 62 | 0 | 12849 | 32 |
| `BenchmarkEndToEndBurst` | 突发 + `Sleep(100µs)` | 256 | 18560 | 62 | 0 | 256 | 32 |
| `BenchmarkSustainedEndToEnd` | 12 producer 持续提交空任务 | 4096 | 1134 | 66 | 0 | 4096 | 32 |

说明：

- `peak-queue`/`peak-workers` 是 1ms 一次的采样峰值，不是精确计数。
- 空任务/短任务/持续提交在 4096 有界队列下进入**背压稳态**：单 producer 的提交速度
  高于 32 个 worker 的消费速度，因此 `peak-queue` 恒等于 `max-buffered`。
  这本身是有意义的观测，但不代表"队列平均值是 4096"。
- `Long`/`Burst` 的 ~19µs/任务 ≈ `Sleep(200µs)` 实测约 0.6ms ÷ 32 个并发 worker。
- `Sustained` 三次结果为 877 / 1134 / 1526 ns/op，方差明显大于批次基准；
  对比时建议同机、同命令、至少 3 次取中位数。

### 9.5 CPU 敏感性（单次 `-cpu=1,4,12`）

| Benchmark | GOMAXPROCS=1 | =4 | =12 |
|---|---|---|---|
| `EndToEndNoop` | 837.1 ns/op | 711.2 | 938.1 |
| `EndToEndShort` | 630.9 | 680.9 | 911.1 |
| `EndToEndLong` | 20984 | 19811 | 19246 |
| `EndToEndBurst` | 21250 | 19339 | 19162 |
| `Sustained` | 837.3 | 719.3 | 1030 |
| `SubmitParallel` | 309.4 | 97.96 | 97.86 |
| `TaskQueuePushParallel` | 54.18 | 92.57 | 88.44 |

`SubmitParallel` 在 `-cpu=1` 时变慢，是因为 producer 与 worker 共享同一个 P；
`TaskQueuePushParallel` 在 1 核时反而最快，原因是单核上 producer 与 consumer 的锁竞争
被调度串行化，不代表队列在 1 核下"更优"。

### 9.6 基准实现过程中的两个坑（记录，避免后续重复踩）

1. **不要用 CPU 忙等模拟长任务**：本机 `busyWait(200µs)` 实测约 2.1ms，
   在低 `GOMAXPROCS` 下被放大得更厉害（探针：1 核 2.24ms、4 核 2.15ms、12 核 1.73ms）。
   长任务改用 `time.Sleep(200µs)`（实测约 0.6ms），更接近阻塞型任务，也不会占满 P。
2. **端到端基准必须预热**：不预热时 producer 在启动阶段会把 4096 缓冲一次灌满，
   `peak-queue` 恒等于 `MaxBuffered`，且 ns/op 混入启动瞬态；预热 Capacity 个任务后，
   峰值和 ns/op 才反映稳态负载。

### 9.9 T4 WaitIdle 记账的开销（A/B，不构成正式性能结论）

用 `my_practice/v5/source/.gotmp/t3check` 下的临时副本移除 `enqueue` 中的
`beginSubmit/endSubmit`（模拟 T3 代码），与 T4 在同一台机器上顺序运行：
`BenchmarkSubmitParallel` 用 `-benchtime=50ms -count=3`；
端到端基准用 `-benchtime=200ms -count=3`、GOMAXPROCS=12。

| Benchmark | T3 等价（无 submitting） | T4（含 submitting） |
|---|---|---|
| `SubmitParallel-2` | 96.7 / 111.0 / 130.0 ns/op | 160.8 / 210.9 / 211.5 ns/op |
| `SubmitParallel-8` | 114.6 / 116.3 / 121.4 ns/op | 191.9 / 192.4 / 192.9 ns/op |
| `EndToEndNoop-12` | 774 / 787 / 995 ns/op | 793 / 806 / 886 ns/op |
| `EndToEndShort-12` | 755 / 961 / 977 ns/op | 778 / 840 / 969 ns/op |

解读：

- 纯提交/空任务基准对额外的两次 `pending.mu` 竞争最敏感（没有任务体，32 个 worker
  同时 `done`），中位数约 +80%，属于最坏情况。
- 端到端基准（含任务执行与 `Close+WaitPool` 排空）的差异落在本机噪声内（9.7 记录过
  2 倍波动），不能据此宣称回归。
- 结论：T4 的开销不影响可测的端到端性能，但提交微基准的成本应在 T9 用 profile 权衡。
  可选方向：批量记账、atomic 快路径，或只对“真正阻塞在满队列”的 Submit 记账
  （后者会缩小“正在提交”的覆盖范围，需先确认语义）。
- 未在 `-race` 下跑 benchmark；未使用 benchstat。

  与 9.4 基线一致，判定为瞬时系统负载，而不是 T8 改动。
- 其余四项与 9.4 的差异在 9.7 记录的噪声范围内（本机同一命令可差 2 倍）。

### 9.11 T9 信号/定时器/块复用 A/B（不构成正式性能结论）

T9 的改动分成三块，用临时副本 `.gotmp/t9base`（T8 代码）与 `.gotmp/t9sig`
（只含信号与 timer 改动，验证后均已删除）做三组交替 A/B：

- **base**：T8 代码；
- **sig**：`notEmpty` 仅空→非空、`notFull` 仅 `pushers>0`、`SubmitBefore` timer 延迟；
- **all**：sig + chunk `recycled` 复用。

方法：同机、GOMAXPROCS=12、`-benchtime=200ms -count=5`，按 base→sig→all 与
all→sig→base 两种顺序各跑多轮，取 ns/op 中位数。

| Benchmark | base（T8） | sig | all（T9） |
|---|---|---|---|
| `SubmitBeforeImmediate`（正序 10 样本） | 834.3 | 348.7 | 350.6 |
| `TaskQueuePushParallel`（正序 10 样本） | 170.8 | 141.9 | 121.8 |
| `SubmitParallel`（正序 10 样本） | 345.3 | 341.4 | 332.4 |
| `EndToEndNoop`（正序 10 / 逆序 15） | 788 / 740 | 775 / 755 | 991 / 726 |
| `EndToEndShort`（正序 10 / 逆序 15） | 953 / 980 | 1054 / 753 | 1004 / 725 |
| `SustainedEndToEnd`（正序 10） | 2366 | 2208 | 2251 |

解读：

- **SubmitBeforeImmediate**：T9 前每个成功提交分配一个 `time.Timer`（3 allocs/op、
  ~298–300 B/op）；T9 后 0 allocs/op、~49 B/op，中位数 ~834 → ~350 ns/op。
- **队列微基准**：170.8 → 141.9 → 121.8 ns/op（信号 + 复用）；方向一致，但绝对值受
  锁竞争与机器负载影响。
- **端到端 ns/op**：正序/逆序差异可达 30%（`EndToEndNoop` 991 vs 726），与 9.7 记录的
  2 倍噪声一致；不能据此宣称 T9 更快或更慢。可确认的是**没有可复现的回归**。
- **分配是 T9 最确定的收益**：有界队列端到端 `B/op` 从 50 降到 0–2
  （Noop/Short/Sustained/Burst）；`BenchmarkEndToEndNoop` 的 2s `alloc_space` 从
  218.66MB（其中 `newChunk` 213.64MB）降到 6.66MB（`newChunk` 0.51MB）。
- 端到端各项 `allocs/op` 一直显示 0：每 64 个任务一次块分配被摊薄后四舍五入，
  `B/op` 才反映块分配差异。
- **`EndToEndLong` 的 `B/op` 仍是 51**：`MaxBuffered=-1` 时队列持续增长，块都仍存活，
  recycled 缓存无法复用；这是预期行为，不是遗漏。
- **CPU profile**（`TaskQueuePushParallel` 2s）：锁竞争仍占主导
  （`Mutex.Lock`+`lockSlow` ~30% cum），`pushLocked` 约 12–15%，
  `memclrNoHeapPointers` 从 ~7% 降到 ~4.8%；无界队列的 `newChunk` 仍占分配大头
  （块未释放），与上面的 B/op 结论一致。

未执行：`-race` 下 benchmark、benchstat、`-count>=10` 的全矩阵；未在 Linux/macOS 验证。

### 9.12 T12 idle 容器 A/B 与 mass timeout 探针（不构成正式性能结论）

T12 的动机是“大量 worker 同时 idle timeout”。先做容器级基准
（`BenchmarkIdleContainer*`，GOMAXPROCS=12，`-benchtime=100ms -count=3`，取中位数）：

| 场景 | stack（T8） | fifo（T12） | 倍数 |
|---|---|---|---|
| `RemoveAll/n=1000` | 45.7 µs | 4.6 µs | ~10x |
| `RemoveAll/n=5000` | 2.84 ms | 24.5 µs | ~116x |
| `RemoveAll/n=10000` | 11.1 ms | 53.3 µs | ~208x |
| `PopAll/n=10000` | 213 µs | 70 µs | ~3x |

- fifo 为 24 B/op、1 alloc/op（基准里每次迭代 `newFIFOIdle` 一次分配；池内只在
  `New` 分配一次）；stack 在 n=10000 时为 310KB/19 allocs（slice 扩容）。
- `RemoveAll` 是“按空闲顺序逐个超时”的模型；stack 每次 O(n) 扫描+搬移，fifo 链表
  任意位置 O(1)。

池级探针（临时副本，Capacity=10000、IdleTimeout=20ms、10000 个阻塞任务，
`release → Running()==0`，各 3 次）：

| 实现 | 耗时 |
|---|---|
| stack（T8 基线） | 43.2 / 44.5 / 43.6 ms |
| 环形缓冲（先尝试，已放弃） | 265.0 / 262.6 / 251.9 ms |
| 双向链表（最终） | 34.2 / 33.1 / 31.4 ms |

- 环形缓冲失败的原因：`pushBack` 与 timer Reset 之间存在调度窗口，超时顺序会与
  队列顺序错位，ring 的“队首快路径”退化为 O(n) 搬移。这与 T9 的教训一致：
  不能只看理想顺序下的复杂度。
- 双向链表的 Remove 不依赖顺序，严格 O(1)；池级比 T8 基线少约 10ms（≈25%）。

普通路径 A/B（stack vs fifo，`-benchtime=200ms -count=5`，两轮共 10 样本中位数）：

| Benchmark | stack | fifo |
|---|---|---|
| `EndToEndNoop` | 1007.5 | 786.8 |
| `EndToEndShort` | 1023.5 | 929.4 |
| `SustainedEndToEnd` | 2407.5 | 2195.5 |
| `SubmitParallel` | 360.2 | 368.5 |
| `TaskQueuePushParallel` | 199.9 | 192.3 |

- 差值落在 9.7 记录的噪声范围内，没有可复现的回归；FIFO 链表没有给普通路径
  增加成本（部分数字偏向 fifo，但不能据此宣称更快）。
- 未在 `-race` 下跑 benchmark；未使用 benchstat；mass timeout 探针未进入正式测试集。

## 10. 兼容性、限制与后续计划

### 10.1 兼容性

- **nil task 行为变更（breaking）**：T2 前 `Submit(nil)` 会被接受并返回 `nil`，
  worker 内 panic 后被 recover；T2 起三个提交接口都返回 `ErrNilTask`。
  迁移：调用方应先检查 `fn != nil`；若要保留"跳过 nil"的行为，自行在提交前过滤。
- **错误优先级变更**：`Close` 之后即使任务 ctx 已取消/已过期，提交也返回
  `ErrPoolClosed`（T2 前可能返回 `context.Canceled` / `DeadlineExceeded`）。
  迁移：用 `errors.Is(err, ErrPoolClosed)` 判断停止提交。
- `Config` 字段与默认值行为不变，只是默认值/校验集中到 `normalizeConfig`。
- 现有示例 `main.go` 不受影响。
- T3 没有公开 API 或提交/关闭语义变化；变化都在包内：任务结果从"被丢弃"变为
  `taskOutcome` 记录，`pending` 计数只在包内可见。唯一的可观测差异是 panic 日志
  现在在扣账之后输出（内容不变）。
- `TestTerminalPathsPoolStaysConsistent` 仍用"执行次数 + queue.size + Running"作为
  一致性代理；pending 归零由 T3 的 `TestPendingZeroAfterCloseAndWait` 单独覆盖。
- **`WaitIdle` 行为变更（T4）**：T4 之前是空实现、调用立即返回；现在会阻塞等待
  “已接受 + 正在提交”的任务归零。把 `WaitIdle()` 当 no-op 使用的代码会开始真正等待；
  若池持续有新任务提交，等待可能持续较久，需要自行控制批次或改用 `Close + WaitPool`。
- **T5 行为变化（无公开签名变化）**：取消/超期任务不再等 worker 释放才进入终态。
  可观测差异：队列中后续任务可能更早开始执行；被跳过任务更早扣减 `pending`，因此
  `WaitIdle` 可能更早返回。`Running()`、队列长度、提交/关闭语义都不变。
- **T6 兼容性**：`Config` 只新增 4 个可选字段（`Logger` / `ErrorHandler` /
  `PanicHandler` / `Hooks`），现有 keyed 字面量无需修改；使用 Config 位置字面量的代码
  需要补零值（本仓库内没有这种用法）。默认行为保持：不配置 hook 时不回调；不配置
  `ErrorHandler` 时 error 仍静默；不配置 `PanicHandler` 时仍输出 panic 日志，但**日志
  现在包含 stack trace，且改用可配置的 Logger**。
- T6 新增导出类型（`TaskResult` / `TaskOutcome` / `Hooks` / `Logger` 等）均为新增，
  没有删除或改签名；`finishTask` 是包内函数，签名从 `finishTask(outcome)` 改为
  `finishTask(task, outcome)`，只影响包内与同包测试。
- T6 的可观测差异：panic 任务现在会进入 `Completed(TaskPanicked)`；被跳过任务只进入
  `Skipped`；`PoolClosed` 在 `Close` 内同步触发，因此一个慢回调会延长 `Close` 的返回时间。
- **T7 兼容性**：只新增 11 个查询方法，没有修改既有方法签名或行为。包内
  `pendingTracker.done` / `endSubmit` 增加参数、`Pool` 增加 `created` 字段；
  累计计数在既有 `pending.mu` 临界区内自增，不改变 `WaitIdle`/`Close`/hook 语义。
  指标读取是只读操作，可以在任意 goroutine（包括 hook）调用。
- **T8 兼容性（无公开 API 变化）**：`p.idle` 从 FIFO（`p.idle[0]` / `p.idle[1:]`）
  改成 LIFO 栈（末尾 pop）。可观测差异只有“哪个空闲 worker 被复用”：
  从最久空闲优先变为最近归还优先；`Running()`/`Idle()`/`Busy()` 的定义与计数不变，
  任务执行顺序、pending 记账、hook 与关闭语义都不受影响。worker 复用顺序不在公开
  契约内，调用方不应依赖它。（T12 又把默认实现改为 FIFO 链表，见下。）
- **T9 兼容性（无公开 API/语义变化）**：只改 `taskQueue` 内部信号策略、timer 创建
  时机与 chunk 复用。提交/关闭/取消的错误与优先级不变（4.5、6.3）；
  `Queued()`/`Pending()` 等指标定义不变。可观测差异只有性能与分配；
  `SubmitBefore` 在队列可写时不再分配 timer。
- **T12 兼容性（无公开 API 变化）**：`Pool.idle` 从 `[]*worker` 换成包内接口
  `idleContainer`，默认 `fifoIdle`（FIFO 双向链表），并保留 `stackIdle` 作为
  包内对照。可观测差异只有“哪个空闲 worker 被复用”：T8 的最近归还优先又变回
  最久空闲优先。该顺序不在公开契约内；`Running()`/`Idle()`/`Busy()` 的定义、
  计数、任务/关闭/pending 语义都不变。容器实现只能包内替换，不新增 `Config` 字段。

### 阶段 1：T2–T5

#### T2（已完成）

- 设计决策：
  - nil task 是调用方参数错误，统一在三个公开入口返回 `ErrNilTask`，不进入队列，
    也不依赖 worker recover；这比"在 queue 内拒绝"更早、更便宜。
  - 错误优先级固定为：参数错误（nil / 非正 timeout）> 池关闭 > ctx > deadline > 队列满。
    "关闭优先于 ctx/deadline"让 Close 之后的提交只有一个稳定答案，producer 循环不需要
    处理多种竞争错误；代价是调用方在池关闭后看不到 ctx 错误。
  - 优先级判定集中到 `queue.push` 的锁内循环：`select` 醒来后回到顶部重判，
    避免 Go `select` 随机选择导致同一竞争场景返回不同错误。
  - 配置默认值与校验集中到 `normalizeConfig`，`New` 只负责构造；零值行为保持不变
    （`MaxChunkLen` 64、`MaxBuffered` 一个 chunk、`IdleTimeout` 1s、`Capacity`/`Mode` 必填）。
- API/内部结构变化：
  - 新增 `ErrNilTask`；
  - 新增常量 `defaultMaxChunkLen`、`defaultIdleTimeout` 和 `normalizeConfig`；
  - `Submit/SubmitCtx/SubmitBefore` 增加 nil 检查；`SubmitBefore` 的 nil 检查先于 timeout；
  - `taskQueue.push` 改为锁内判定 `closed → ctx → deadline → 空间/ErrPoolFull`，
    并从 `select` 回到循环顶部重判。
- 关键不变量与时序：
  - 被拒绝的提交不改变 `queue.taskNum`、不创建 worker、不做 pending 记账；
  - `closed` 一旦在锁内置位，任何后续 push 都返回 `ErrPoolClosed`，与 ctx/deadline 无关；
  - `woke` 的 `notFull` 归还只在"消费了空位提示但最终因 ctx/deadline 未入队"时发生；
    因 closed 返回时不需要归还（`closedCh` 广播会唤醒所有等待者）；
  - `ctx.Err()` 在 `queue.mu` 外读取，避免用户自定义 Context 的方法在锁内执行；
    因此"读取后、加锁前"取消的任务仍可能入队，由 dispatcher/worker 的 `abortErr` 跳过。
- 修改文件：`pool_interface.go`、`task_queue.go`；新增 `pool_api_test.go`；
  从 `pool_regression_test.go` 移除旧的 `TestNilTaskCurrentBehavior`。
- 测试与验收：
  - 8 个新测试全部通过；全量 37 个测试、`-count=3 -cpu=1,2,8`、`-race` 均通过；
  - 命令与结果见 9.2；热路径 spot-check 见 9.7（不构成性能结论）。

#### T3（已完成）

- 设计决策：
  - **结果分类与记账分离**：`runTask` 只负责产生 `taskOutcome`（completed/error/
    panic/canceled/deadline-skipped），`finishTask` 是所有终态的唯一入口。它先
    `pending.done()`，再做 panic 日志等副作用，保证 logger/hook 异常不绕过记账。
  - **接受与 +1 原子化**：pending 只在"任务已写入 chunk"的同一临界区（`pushLocked`
    内回调 `onAccept`）增加。因此拒绝路径天然不记账，也不会出现"dispatcher 先 pop
    扣账、提交方才 +1"的负计数窗口。实现初期曾把 +1 放在 `Submit` 入口，
    `TestPendingExcludesBlockedSubmit` 暴露了它与 T0 第 1 条冲突，随后改为当前方案。
  - **dispatcher 两条丢弃路径统一**：pop 后立即发现取消/超期、以及等 worker 期间
    发现取消/超期，都走 `outcomeForAbort + finishTask`，不再静默 `continue`/`return`。
  - **可重建 drain channel**：`pendingTracker` 在 0→1 时换新 channel、减到 0 时关闭，
    支持多批次等待；T3 只做内部实现，公开 `WaitIdle` 留给 T4。
- API/内部结构变化：

### 阶段 2：T6–T7

#### T6（已完成）

- 设计决策：
  - **构造期固定的观测配置**：Logger/ErrorHandler/PanicHandler/Hooks 都放在 `Config`，
    `New` 之后只读。热路径不需要 atomic 或锁，也不会出现“运行中替换 hook”与 worker
    读取之间的数据竞争；代价是不支持运行期注册。
  - **hook 用可空 func 字段的结构体，而不是接口**：`Hooks{Submitted: ...}` 只填需要的
    事件，避免为 5 个方法写空实现，也不引入上游式 dispatcher 的间接层。
  - **Submitted 与 Enqueued 分离**：Submitted 在 `push` 前触发（所有合法尝试，包括
    随后被拒绝的提交），Enqueued 只在 push 成功后触发。这样背压/关闭拒绝可观测，
    同时 Enqueued 仍严格表示“已接受”。
  - **Enqueued 在 `queue.mu` 释放后触发**：用户回调绝不能在锁内执行；代价是
    `Enqueued` 与 `Started` 可能乱序（与上游相同的取舍）。
  - **skipped 独立成 Skipped hook**：保持 T0 第 2 条“Completed 不覆盖 skipped”；
    `TaskOutcome.Result` 区分 canceled / deadline-skipped。
  - **记账先于回调**：`finishTask` 先 `pending.done()` 再 `observeOutcome`；慢、阻塞或
    panic 的回调都不会让 `WaitIdle` 永久等待，也不会漏记账。
  - **panic stack 在 recover 点捕获**：`runTask` 的 defer 内调用 `debug.Stack()`，
    避免栈展开后丢失 panic 位置；stack 只交给 PanicHandler/默认日志，不放进
    `TaskOutcome`。
  - **每个回调单独 recover**：`safeCallback` 隔离 hook/handler panic；Logger 自身
    panic 在 `logf` 中再次被吞掉，诊断路径不会变成新的崩溃源。
  - **重试与 hook 的预决策**：T10 的重试属于同一逻辑任务，五个事件 hook 各触发一次；
    这样 hook 计数等于被接受任务数，Started/Completed 始终成对，与一次 pending 记账一致。

### 阶段 3：T8–T9

#### T8（已完成）

- 设计决策：
  - **选择 LIFO 栈（方案 A）**：`p.idle` 的注释原来写“slice 当栈用”，实现却从头部
    `p.idle = p.idle[1:]` 弹出（FIFO）。选择让实现向注释靠拢，而不是引入 ring queue。
    理由：worker 复用顺序不属于公开语义；append + 末尾 pop 已经复用容量；ring queue
    的 O(1) 头部 pop 只在超大 `Capacity` 与高频“空闲↔认领”交替时才有收益，当前没有
    基准证据；可插拔容器留给 T12。
  - **pop/remove 清槽**：pop 取末尾后把该槽置 nil；remove 先 `copy` 保持其余元素栈序，
    再把尾部槽置 nil 后截断。这样 `p.idle[len:cap]` 恒为 nil，底层数组不会保留已退出
    或被认领的 worker 及其 `tasks` channel。
  - **空栈保留容量**：栈空时不把 `p.idle` 置 nil，保留底层数组容量供下一轮突发复用；
    槽位已清空，不构成 worker 引用；容量上界由 `Capacity` 决定。
  - **不改交接协议**：被 pop 的 worker 仍必须恰好收到一个任务；timeout 与 dispatcher
    同时认领时 `removeIdle` 返回 false 的分支保持不变（6.2/6.4）。
  - **测试直接检查底层槽位**：`idle_test.go` 在 `p.mu` 内复制 `p.idle[:cap]`，断言
    size 之外全为 nil；纯黑盒测试无法发现“len 正确但底层数组仍持有引用”。
- API/内部结构变化：
  - 新增 `pushIdleLocked` / `popIdleLocked` / `removeIdleLocked`（都要求持有 `p.mu`）；
  - `pushBack` 改用 `pushIdleLocked`，dispatcher 的 idle 分支改用 `popIdleLocked`，
    `removeIdle` 变成加锁包装；
  - `Pool.idle` 注释改为 LIFO 栈；`metrics.go` 的 `Idle` 文档补充“不反映栈序”；
  - 没有公开签名变化。
- 关键不变量与时序：
  - `p.idle[0:len]` 元素非 nil 且每个空闲 worker 恰好一次；`p.idle[len:cap]` 全 nil；
  - 只有 dispatcher 在 `p.mu` 内 pop；只有 worker 自己 push/remove；
  - 被 pop 的 worker 仍满足“恰好收到一个任务”的交接保证；
  - worker 超时退出与 dispatcher 认领竞争时，`removeIdleLocked` 在 `p.mu` 内判定

  - **`notEmpty` 只在空→非空时发送**：`push` 在锁内记录 `wasEmpty`；队列非空时 pop
    要么正在处理、要么下一次循环会看到，不需要每次 push 都唤醒。
  - **`notFull` 只在有阻塞提交者时发送**：新增 `q.pushers`，由 `queue.mu` 保护。
    提交者在“锁内判定为满”的同一临界区 `pushers++`，pop 在锁内读 `pushers` 后仅在
    有等待者时发信号；这样既避免每次 pop 无条件碰 notFull，又不会出现“pop 释放空位
    但看不到等待者”的丢唤醒窗口。
  - **取消不吞唤醒**：提交者消费到 notFull token 却因 ctx/deadline 返回时，
    `forwardNotFull` 把提示转交其他等待者；`woke` 只表示本次 select 是否真的消费了
    提示，避免跨轮次误转发。
  - **timer 延迟创建**：`SubmitBefore` 的 `time.Timer` 只在首次进入“队列满、需要
    select”时创建；队列立即可写时零 timer 分配。这是 T9 最确定的收益
    （3 allocs/op → 0，~834 → ~350 ns/op）。
  - **chunk 复用用队列内 free list，而不是 sync.Pool**：chunk 生命周期已经由
    `queue.mu` 保护，free list 无额外同步、无 per-P 重复、内存上界可解释；上限
    `maxRecycledSlots=4096` 个槽位，关闭时清空。
  - **不把 chunk 分配移出锁**：只有缓存未命中才分配；锁外预分配或“分配后重查 tail”
    都增加复杂度，且没有基准支持。
- API/内部结构变化：
  - `taskQueue` 新增 `pushers int`、`recycled []*chunk`，以及 `getChunkLocked`、
    `recycleChunkLocked`、`forwardNotFull`；`pushLocked`/`popLocked` 接入块复用，
    `close` 清空 `recycled`；
  - `push` 的信号策略与 timer 创建时机调整；`pop` 按 `pushers` 决定是否发 notFull；
  - 新增 `pool/benchmark_submitbefore_test.go`；`task_queue_test.go` 增加 2 个测试；
  - 没有公开 API 或签名变化。
- 关键不变量与时序：
  - `pushers` 的登记与“判定为满”在同一临界区；等待者被唤醒后先 `pushers--`，再在
    下一轮锁内重新检查空间/满；任何 pop 释放的空位要么被该等待者看到，要么被登记的
    等待者收到提示。
  - `notEmpty` 的空→非空判断在锁内完成（`wasEmpty := taskNum == 0`）。
  - `recycled` 只接受 `count == 0` 的块；块内槽位在 pop 时已置零，不残留 task；
    关闭后不再回收，并把已有缓存置 nil。
  - `recycled` 不计入 `taskNum`/`MaxBuffered`，不改变队列容量语义。
- 修改文件：`pool/task_queue.go`、`pool/task_queue_test.go`；新增
  `pool/benchmark_submitbefore_test.go`。
- 测试与验收：
  - 92 个测试、8 个基准；`gofmt -l pool` 无输出、`go vet ./...` 通过；
  - `go test ./...`、`-count=3 -cpu=1,2,8`、`-race -count=10`（含 100k 压测）、
    T9 专项 `-race -count=20` 与非 race `-count=50` 全部通过；
  - 命令与结果见 9.2；新增测试见 9.3；A/B 见 9.11。
- 遗留：
  - 端到端 ns/op 噪声大，T9 只能证明“无可复现回归”，不能证明变快；确定收益是
    SubmitBefore 的 timer 分配与有界队列的 chunk 分配（B/op 50→0–2）。
  - 无界队列增长时 chunk 仍全部分配（B/op 51）；recycled 只对“有块被消费完”的
    场景有效。
  - `queue.mu` 锁竞争仍是主要成本；批量消费/handoff/sharding 属 T11/T14。
  - 未在 `-race` 下跑 benchmark，未使用 benchstat。

#### T12（已完成）

- 设计决策：
  - **只做包内可插拔**：`Pool.idle` 从 `[]*worker` 换成包内接口 `idleContainer`
    （Add/Pop/Remove/Len），构造期选定；新增 `newPool(cfg, idle)` 供包内测试替换
    实现；不新增公开 `Config` 字段。
  - **默认 FIFO + 双向链表，而不是 ring**：目标场景是大量 worker 同时 idle timeout。
    先实现 ring（队首 O(1)），但池级探针显示 timeout 顺序与队列顺序会因
    `pushBack` 与 timer Reset 之间的调度窗口错位，端到端 252–265ms，比 T8 的 stack
    还慢；改为双向链表后 Remove 不依赖顺序，池级 31–34ms（9.12）。
  - **节点内嵌在 worker 上**：`idlePrev/idleNext/idleLinked` 三个字段，Add/Pop/Remove
    零分配；容器不额外分配节点。
  - **保留 `stackIdle` 作为对照**：T8 的 LIFO 实现留在包内，测试/基准可替换对比，
    并用于验证“不同实现语义一致”。
  - **接口不含 `RemoveExpired`**：v5 的 idle timeout 由每个 worker 自己的 timer
    驱动，容器不保存 idle 起始时间、也不关闭 worker；引入 `RemoveExpired` 需要同时
    改 worker 退出协议（quit + 池级 reaper），不在本轮范围。这是对规划 T12 顺序
    建议的有意调整，理由是保持 T8 已固定的 timeout 语义。
- API/内部结构变化：
  - 新增 `idle_container.go`：`idleContainer`、`stackIdle`、`fifoIdle`；
  - `worker` 增加 3 个 idle 链表字段；
  - `Pool.idle` 类型改为接口；`New` 拆出 `newPool(cfg, idle)`；`Idle()`/`Busy()`
    改用 `idle.Len()`；
  - `idle_test.go` 重写为容器级 + 池级等价测试；新增 `idle_benchmark_test.go`；
  - 没有公开 API 或签名变化。
- 关键不变量与时序：
  - 所有容器方法在 `p.mu` 内调用，容器自身不加锁；
  - 每个空闲 worker 在容器中恰好一次；Pop/Remove 清空节点或槽位；
  - Remove 返回 false 表示已被 dispatcher 认领，worker 继续等任务；
  - 默认 FIFO 只改变“复用哪个 worker”，不改变任务/关闭/pending 语义。
- 修改文件：`pool/pool_interface.go`、`pool/metrics.go`（注释）；新增
  `pool/idle_container.go`、`pool/idle_benchmark_test.go`；重写 `pool/idle_test.go`。
- 测试与验收：
  - 94 个测试、10 个基准；`gofmt -l pool` 无输出、`go vet ./...` 通过；
  - `go test ./...`、`-count=3 -cpu=1,2,8`、`-race -count=10`（含 100k 压测）、
    T12 专项 `-race -count=20` 与非 race `-count=50` 全部通过；
  - 容器删除 10k 从 11.1ms 降到约 53µs；池级 mass timeout 从约 43ms 降到 31–34ms；
    普通路径无可复现回归；命令与结果见 9.2/9.3/9.12。

  - 容器只能包内替换，不暴露给调用方；目前只有 stack/fifo 两种实现；
  - 无 `RemoveExpired`/池级 reaper；idle timeout 精度与 T8 相同（每 worker timer）；
