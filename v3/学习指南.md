# Worker Pool V3 —— 复现辅助文档

> 目标：worker **按需创建、闲置自动回收**，这是 ants / agilePool 这类库的核心雏形。
> 前置：V2 验收标准全部通过。
> 新增知识：`select` 多路复用、`time.Timer` / `time.After`、用锁保护共享状态、原子计数。

---

## 一、设计变化的本质

V1/V2 的模型：**池子创建时启动 N 个 worker，大家从一个共享 channel 抢任务。**

V3 的模型改成：**池子初始是空的。来一个任务，先看有没有空闲 worker，没有就新建一个（直到达到容量上限）。worker 空闲超过一定时间就自行退出。**

这个转变带来三个必须想清楚的变化：

1. **任务不再直接进 channel**。Submit 的第一步变成"找一个 worker"。找不到怎么办？（阻塞等待 / 新建 / 超限后排队——V3 选"阻塞等待空闲worker"，排队缓冲是 V5 的内容）
2. **"空闲 worker"是一份共享状态**。多个 goroutine 并发取/还 worker，这份状态怎么保护？
3. **worker 的退出条件变了**：不再是"channel 关闭"，而是"空闲超时"或"池子关闭"。一个 worker 如何同时监听三件事（新任务 / 超时 / 关闭）？

## 二、要实现的接口

```go
package pool

type Config struct {
    Capacity    int           // worker 数量上限
    IdleTimeout time.Duration // 空闲多久自动退出
}

type Pool struct {
    // TODO: 思考字段。提示：至少需要一个"当前worker数"的计数、
    // 一个"空闲worker"集合、一把锁、关闭信号
}

func New(cfg Config) *Pool
func (p *Pool) Submit(task func()) error
func (p *Pool) Close()
func (p *Pool) Wait()

// Running 返回当前存活的 worker 数（用于测试和观察）
func (p *Pool) Running() int
```

关键行为：

```go
p := pool.New(pool.Config{Capacity: 10, IdleTimeout: time.Second})
fmt.Println(p.Running()) // 0 —— 创建时一个 worker 都没有

p.Submit(func() { time.Sleep(100 * time.Millisecond) })
fmt.Println(p.Running()) // 1

time.Sleep(2 * time.Second)
fmt.Println(p.Running()) // 0 —— 闲置超时，worker 已退出
```

## 三、结构设计：回答四个问题

1. **worker 和任务之间用什么连接？**
   V1 是"所有 worker 共享一个任务 channel"。V3 推荐改成：**每个 worker 有自己的任务 channel**（容量为 1）。池子把空闲 worker 放进一个集合，Submit 从集合里取一个 worker，往它的 channel 发任务。想想为什么这样比共享 channel 更适合"回收"语义。

2. **空闲集合用什么数据结构？**
   V3 用 slice 当栈/队列即可。但注意 agilePool 提供了链表、最小堆、Treap、环形队列五种——它们优化的是"回收时按最后活跃时间清理"的效率。V3 用 slice + 每次用完更新位置就够了，别提前优化。

3. **worker 的主循环长什么样？**
   大致是：

   ```
   for {
       执行刚到手的任务
       把自己放回空闲集合        // 需要锁
       select {
       case 新任务:   继续循环
       case 超时:     从集合移除自己，退出   // 需要锁
       case 池子关闭: 退出
       }
   }
   ```

   这个循环里藏着一个微妙的竞态，见易错点 1——这是 V3 最值得想清楚的地方。

4. **`Running()` 的计数怎么维护？**
   新建 worker +1，worker 退出 -1。这个计数会被多个 goroutine 读写，用 `sync/atomic` 还是放进锁里？（都可以，说出你选的理由）

## 四、分层提示（卡住时逐级查看）

<details>
<summary>提示 1：Submit 的决策流程</summary>

```
Submit(task):
    锁内：尝试从空闲集合弹出一个 worker
    如果弹到了 → 往该 worker 的 channel 发任务，返回
    如果没弹到且 Running < Capacity → 新建 worker，直接让它执行，返回
    否则 → 阻塞等待（等某个 worker 空闲出来）
```

"阻塞等待"这一步 V3 可以用一个容量为 Capacity 的信号量 channel 实现，或者干脆 `for { try; runtime.Gosched() }` 自旋。想优雅可以查 `sync.Cond`，但 V3 不强制。
</details>

<details>
<summary>提示 2：超时用 time.NewTimer，不要用 time.After</summary>

`time.After` 每次调用都创建一个 timer，在循环里频繁使用会有资源泄漏（旧 timer 要等到期才回收）。在循环外用 `time.NewTimer`，每轮 `Reset`。查一下 `Timer.Reset` 的正确用法和它在 Go 1.23 前后的语义变化。
</details>

<details>
<summary>提示 3：归还与取出的竞态（V3 核心难点）</summary>

场景：worker 刚把自己放回空闲集合，正准备进入 `select` 等待；与此同时 Submit 把它从集合里取出来并发送任务。如果 worker 的 select 还没准备好接收，会怎样？

因为每个 worker 的任务 channel **容量为 1**，Submit 的发送不会阻塞——任务在缓冲里，worker 进入 select 后立刻读到。这就是容量 1 存在的意义。

再追问一步：worker 超时退出时，要把自己从空闲集合里删掉。如果它**已经被 Submit 取走**（不在集合里了）但还没收到任务，此时超时触发会怎样？怎么避免"把正在干活的 worker 杀掉"？（提示：worker 被取走时就该停止计时/退出 select 分支，想想 select 的结构怎么天然保证这一点）
</details>

<details>
<summary>提示 4：Close 时怎么让所有 worker 退出</summary>

关闭一个"池子关闭信号" channel，worker 的 select 里有对应分支。注意区分：空闲中的 worker 直接退出；正在执行任务的 worker 应该跑完手头任务再退出——这个语义怎么从代码结构里自然得到？
</details>

## 五、易错点（写完逐条自查）

1. **放回与取出的竞态**：用提示 3 的场景，写测试验证——高并发 Submit + 极短 IdleTimeout，跑 10 万次，`Running()` 最终必须归零且无 panic。
2. **死锁形态**："锁内做 channel 发送"是常见死锁来源。检查你的代码：拿锁的区间里有没有可能阻塞的操作？（容量 1 的 channel 发送在"刚取出"时不阻塞，但如果 worker 已被取走又超时退出……画出状态转换再确认）
3. **计数泄漏**：跑完所有任务 + 等待超时后，`Running()` 必须为 0。写一个反复 Submit/闲置 100 轮的测试断言这一点。
4. **timer 泄漏**：用 `go test -race` 之外，试试在测试里用 `runtime.NumGoroutine()` 前后对比，确认 worker 都退干净了。

## 六、验收标准

- [ ] 创建池子时 `Running() == 0`，首个任务到来才创建 worker
- [ ] 突发 10 个并发任务时 `Running()` 涨到 10；达到 Capacity 后多出的任务阻塞等待而非创建新 worker
- [ ] 闲置超过 IdleTimeout 后 `Running()` 归零
- [ ] `Close()` 后：空闲 worker 立即退出，执行中的 worker 跑完再退出，`Submit` 返回 error
- [ ] 压测测试（10 万任务、Capacity=100、超时 50ms）在 `-race` 下通过，结束后 goroutine 数量回落
- [ ] 能画出 worker 的完整状态机：创建 → 执行 → 空闲 → (被取走 | 超时退出 | 关闭退出)

## 七、完成后：对比 agilePool

V3 完成后，打开 agilePool 源码（`pool.go`、`worker.go`），对照这几处：

1. 它的空闲容器接口和你 slice 方案的对应关系——为什么它把容器抽象成可插拔接口？
2. 它的 worker 超时清理是"后台 cleaner 定期扫描"而不是 worker 自己计时——两种方案的权衡是什么？（提示：10 万个 worker 时，10 万个 timer 意味着什么）
3. 它的 `Submit` 在找不到 worker 时走的是"任务进缓冲队列"而非"阻塞等待"——这是 V5 的方向，先记住这个差异。

读完这几处，你对"为什么这个库比玩具版本复杂"会有具体的认识，而不是模糊的感觉。
